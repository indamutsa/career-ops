# B10 — Teaching it to reason

B9 taught your model to *respond*. This lesson teaches it to *think before responding*, and then
improves that thinking with reinforcement learning against a programmatic verifier.

This is the small-scale version of what DeepSeek did in 2025, and the reason it works at 3.4M
parameters is the same reason it works at 671B: **the reward is computed by a program, not a
learned model.** No human preference labels, no reward model, no annotation budget. A generated
problem carries its own gold answer, so correctness is checkable exactly.

The capability ceiling here is low — synthetic transitivity puzzles and small arithmetic, not
mathematics. But the *machinery* is complete and identical, and you will observe the response-length
growth that made R1-Zero famous, on your own model.

Reference companions: [Module 15](../15-rlvr-grpo.md), [Module 15a](../15a-deepseek-r1.md),
[Module 14](../14-preference.md).

---

## Terms

| Term | Meaning |
|------|---------|
| **Chain of thought (CoT)** | Intermediate reasoning tokens emitted before the answer. |
| **Scratchpad** | The `<thought>` block, treated as working memory. |
| **Process supervision** | Training on the reasoning steps, not only the final answer. |
| **Outcome supervision** | Training on the final answer only. |
| **Synthetic data** | Problems generated by a program that also knows the answer. |
| **Verifier** | A function `(completion, gold) → reward`. Deterministic, programmatic. |
| **RLVR** | RL from Verifiable Rewards. The verifier replaces the reward model. |
| **GRPO** | Group Relative Policy Optimization — advantage from a group mean, no value network. |
| **Group** | The `k` sampled completions for one prompt. |
| **Zero-variance group** | All `k` completions get identical reward → advantage 0 → no signal. |
| **KL penalty** | Term keeping the policy near the reference model. |
| **Reward hacking** | Maximising the reward without the intended capability. |
| **pass@k** | Fraction of problems solved within `k` samples. Creation vs selection. |

---

## Concepts

### Why a scratchpad works at all

A transformer does a fixed amount of computation per token: `n_layers` blocks, no loops, no
recursion. There is no mechanism for "think harder about this one token".

Chain of thought is how the architecture escapes that limit. **Generating intermediate tokens
converts a fixed-depth computation into a variable-length one** — the model writes a partial result,
then attends to its own writing on the next step, and the residual stream carries state forward
through text rather than through depth.

That framing also predicts exactly when CoT helps and when it doesn't: it helps on problems requiring
serial steps that exceed what `n_layers` can do in one pass, and does nothing for problems answerable
by lookup. It also predicts the failure mode — once a wrong step is written it is conditioned on,
so errors compound rather than cancel.

Your own B4 causal-mask work is what makes this concrete: attention at position `t` can read every
scratchpad token before it. **The scratchpad is working memory implemented in the KV cache.**

### Synthetic logic data: the generator knows the answer

The reason you can teach a 3.4M model to reason at all is that you are not scraping reasoning — you
are *generating* it, with a program that produces the problem, the correct chain of thought, and the
answer simultaneously.

```python
import random

def make_transitivity(n=3):
    names = random.sample(["A", "B", "C", "D", "E"], n)
    random.shuffle(names)                                    # heaviest → lightest
    facts = [f"Box {names[i]} is heavier than Box {names[i+1]}." for i in range(n - 1)]
    random.shuffle(facts)                                    # order must not give it away
    chain = " > ".join(names)
    thought = ("Track the weights. " + " ".join(facts) +
               f" Chaining these gives {chain}. The lightest is {names[-1]}.")
    return {
        "instruction": "Solve the puzzle.",
        "input": " ".join(facts) + " Which box is lightest?",
        "thought": thought,
        "response": f"Box {names[-1]} is the lightest.",
        "gold": names[-1],
    }
```

Four rules that make the difference between a dataset that teaches reasoning and one that teaches a
shortcut:

- **Shuffle the premises.** If the facts always appear in chain order, the model learns "answer is the
  last-mentioned box" and scores 100% having learned nothing. This is the single most common way a
  synthetic reasoning set is silently broken, and Lab 2 catches it.
- **Vary the surface form** — heavier/lighter, older/younger, taller/shorter. Otherwise you are
  training a template matcher.
- **Vary the difficulty** — 3, 4, 5 items. Fixed difficulty gives you no generalisation curve and no
  way to distinguish learning from memorising.
- **Every example carries `gold`.** That field is what makes Phase 3 possible without any human
  labelling.

Generate arithmetic the same way: multi-step addition, digit reversal, sorting — anything a
twenty-line Python function can solve and narrate.

### The three phases, and what each buys

| Phase | Data | Signal | Teaches |
|-------|------|--------|---------|
| **Pretrain (B6)** | Raw text | Next token | Grammar, vocabulary, association |
| **SFT+CoT (here)** | `(prompt, thought, response)` | Next token, masked to completion | *Format* of reasoning |
| **RLVR (here)** | `(prompt, gold)` | Programmatic verifier | *Quality* of reasoning |

**The distinction between the second and third rows is the one interviewers probe.** SFT can only
imitate the chains you wrote; it cannot discover a better one, and its ceiling is your generator's
quality. RL optimises for *being right*, so it can find strategies absent from the SFT data — which
is precisely what "the model learned to check its own work" means in the R1 write-ups.

### Reward design, and the length trap

```python
import re

def reward(completion, gold):
    r = 0.0
    if "<thought>" in completion and "</thought>" in completion:
        r += 0.2                                     # format
    m = re.search(r"<response>(.*?)</response>", completion, re.S)
    if m:
        r += 0.2                                     # well-formed answer block
        if gold.lower() in m.group(1).lower():
            r += 1.0                                 # correctness dominates
    return r
```

**There is deliberately nothing about length in this function.** That is not an oversight — it is the
experiment. In Lab 5 you log mean completion length per step, and you should see it grow anyway,
because longer reasoning happens to be more often correct and correctness is what is rewarded. That
emergent length growth, with no length term in the reward, is the single most-cited observation from
R1-Zero, and reproducing it on your own model is worth more than reading about it ten times.

The counterpart risk is **reward hacking**. If `gold` is a single letter and you check substring
containment, a completion that lists every letter scores 1.0. Lab 7 makes you break your own reward
this way on purpose, because the instinct to attack your own metric is the actual skill.

### GRPO in one paragraph

PPO needs a learned value network to compute advantages — a second model, roughly the size of the
first, trained alongside it. GRPO removes it: **sample `k` completions for the same prompt and use
the group's mean reward as the baseline.**

```python
rewards = torch.tensor([reward(c, gold) for c in completions])   # (k,)
advantages = (rewards - rewards.mean()) / (rewards.std() + 1e-8)
```

Two properties follow immediately, and both are interview material:

- **Half the memory and none of the value-network instability**, which is why GRPO became the default
  for verifiable-reward RL. Note the attribution: GRPO is from **DeepSeekMath (2024)**, not R1.
- **Zero-variance groups give zero signal.** If all `k` completions are correct, or all wrong, the
  advantage is exactly zero and the batch teaches nothing. On easy problems you burn compute for
  free; on impossible ones likewise. Curriculum difficulty is therefore not a nicety — it is what
  keeps the gradient alive, and Lab 6 has you measure the wasted fraction.

---

## Where it's used

- DeepSeek-R1, o-series-style reasoning models, and every open reasoning model since.
- Code generation with unit tests as the verifier — the cleanest RLVR domain there is.
- Math with symbolic answer checking.
- Agentic training, where the verifier is "did the task complete".
- Anywhere a program can grade the output. Where it cannot, you are back to RLHF (Module 14).

## Labs

### Lab 1 — The generator

Write generators for four families, 2,000 examples each, with a held-out set at *higher* difficulty
than training (train on 3–4 items, test on 5).

| Family | Task |
|--------|------|
| Transitivity | "A > B > C, which is lightest?" |
| Multi-step arithmetic | "Add 17 and 25, then subtract 9." |
| Reversal | "Reverse the digits of 4821." |
| Sorting | "Order these by size: …" |

**Testing at a difficulty never seen in training is what separates reasoning from pattern-matching**,
and it is the only measurement in this lesson that can distinguish them.

### Lab 2 — Break your own dataset first

Before training on it, attack it:

1. Train a **premise-order baseline**: always answer with the last-mentioned entity.
2. Train a **bag-of-words baseline** on the input text only.

**If either scores well above chance, your generator leaks and the lesson is void.** Fix the
generator and re-run. Doing this before training rather than after is the habit that matters — it is
the same instinct as B3's leaky-split lab, applied to a reasoning set.

### Lab 3 — SFT with thought supervision

Fine-tune `ckpt_instruct.pt` on the CoT data using B9's masking (loss on `<thought>` and
`<response>`, prompt masked).

Then evaluate three ways, which is the actual experiment:

| Condition | Measures |
|-----------|----------|
| With `<thought>`, scored on final answer | Full CoT performance |
| Forced to answer immediately (thought suppressed) | Value of the scratchpad |
| Thought present but **scrambled** at inference | Whether the model reads it or just emits it |

**The third condition is the sharp one.** If scrambling the scratchpad doesn't hurt accuracy, your
model is producing reasoning-shaped decoration and attending to none of it — a real and widely
observed failure that the first two conditions cannot detect.

### Lab 4 — GRPO loop

```python
for step in range(N_STEPS):
    prompt, gold = sample_problem()
    completions = [generate(policy, prompt, temperature=1.0, top_p=0.95) for _ in range(K)]
    rewards = torch.tensor([reward(c, gold) for c in completions])

    if rewards.std() < 1e-6:
        zero_var += 1
        continue                                    # no signal in this group

    adv = (rewards - rewards.mean()) / (rewards.std() + 1e-8)
    logp = token_logprobs(policy, completions)       # sum over completion tokens
    with torch.no_grad():
        ref_logp = token_logprobs(ref_model, completions)

    pg_loss = -(adv.unsqueeze(1) * logp).mean()
    kl      = (logp - ref_logp).mean()
    loss    = pg_loss + BETA * kl
    loss.backward(); opt.step(); opt.zero_grad(set_to_none=True)
```

Start with `K=8`, `BETA=0.02`, `lr=1e-6`. **RL learning rates are another order of magnitude below
SFT's** — at 1e-5 the policy collapses within a hundred steps, and it is worth seeing that once
deliberately.

Freeze `ref_model` as a copy of the SFT checkpoint. Without the KL term the policy drifts off
distribution and output degenerates while reward climbs, which is the clearest possible illustration
of why the term exists.

### Lab 5 — Watch the response length grow

Log per step: mean reward, mean completion length, format-compliance rate, zero-variance fraction.

| Step | Reward | Mean length | Note |
|------|--------|-------------|------|
| 0 | ~0.4 | ~40 tok | Format only |
| 200 | ~0.7 | ~55 tok | Correctness rising |
| 500 | ~0.9 | ~80 tok | **Longer reasoning, unrewarded directly** |
| 1000 | ~1.1 | ~95 tok | Plateau near verifier ceiling |

**Plot length against step and confirm nothing in your reward function mentions length.** This is
R1-Zero's headline observation, reproduced at 3.4M parameters. Note in your write-up how many steps
it took to appear.

### Lab 6 — Zero-variance groups

Sweep `K = 4, 8, 16` and difficulty easy/medium/hard, logging the fraction of groups skipped.

**Expect: easy problems produce all-correct groups, hard problems all-wrong, and both waste the
batch.** Compute the fraction of compute doing nothing, then build a curriculum that samples
difficulty to keep groups mixed, and re-measure. That efficiency gain is a concrete, quantified
result — exactly the kind of thing worth describing in an interview because most people know the
concept and have never measured it.

### Lab 7 — Hack your own reward

Deliberately exploit `reward()`:

1. Emit every candidate letter inside `<response>` — substring containment scores 1.0.
2. Emit an empty `<thought></thought>` — collects the format reward for nothing.
3. Pad with irrelevant text if you ever added a length bonus.

Then harden it: exact match after normalisation, one answer only, a minimum non-trivial thought, and
a check that the answer is in the valid entity set.

**Re-run RL with the hardened reward and compare.** The lesson to state plainly: the verifier is your
true objective function, and the policy will find every gap in it. Every reward-hacking incident in
the literature is this lab at scale.

### Lab 8 — pass@k: creation or selection?

For the SFT model and the RL model, sample `k = 1, 4, 16, 64` per problem and compute pass@k on the
held-out *harder* set.

- **RL wins decisively at k=1** — it concentrates probability on correct reasoning.
- **The pass@64 gap is much smaller**, and may vanish.

That is the sharpest open question in the field, and having your own numbers is a genuinely strong
position to argue from: **if RL only sharpens what the base model could already produce, it is
selection; if pass@64 also improves, something was created.** State which your data supports, at your
scale, with the caveat that a 3.4M model on synthetic puzzles cannot settle the general case.

### Lab 9 — Distil it back

Generate 5,000 correct completions from the RL model, filter by verifier, and SFT the *base*
checkpoint on them.

**Compare against running RL on that base model directly.** In R1's results distillation won — the
reasoning was cheaper to copy than to rediscover. Report which wins at your scale; either outcome is
informative and you should say which you got.

## Failure modes

| Symptom | Cause | Fix |
|---------|-------|-----|
| Baseline heuristic scores well | Generator leaks | Shuffle premises, vary surface form |
| Scrambling the thought doesn't hurt | Model ignores its own scratchpad | Harder problems; check attention to thought tokens |
| Reward rises, output degenerates | No KL, or `beta` too small | Add/raise the KL penalty |
| Policy collapses in ~100 steps | RL LR too high | 1e-6, not 1e-5 |
| Most groups skipped | Difficulty mismatched to ability | Curriculum sampling |
| Perfect reward, useless model | Reward hacking | Harden the verifier; Lab 7 |
| Length explodes without accuracy | Length rewarded directly or indirectly | Remove length terms; cap generation |
| Reasoning correct, answer wrong | Answer extraction brittle | Strict `<response>` parsing |
| Gains don't transfer to harder held-out | Memorising templates | Vary difficulty and phrasing |
| Nothing improves at all | Verifier too strict — reward always 0 | Log the reward distribution first |

## Interview

**"How would you teach a small model to reason?"**
Two stages after pretraining. First supervised fine-tuning on `(prompt, thought, response)` triples so
it learns to emit reasoning before an answer — that teaches the format, and its ceiling is whatever
chains you wrote. Then RL with a programmatic verifier, which optimises for being *right* rather than
for imitating, so it can find strategies the SFT data never contained. The reason this is tractable
at small scale is that I generate the problems with a program that also produces the gold answer, so
verification is exact and free — no reward model, no human labels. I built exactly this on a 3.4M
model I pretrained myself: transitivity and arithmetic puzzles, SFT for the format, then GRPO against
a verifier.

**"Why does chain of thought help at all?"**
A transformer does a fixed amount of computation per token — `n_layers` blocks, no loops. There's no
way to think harder about one token. Generating intermediate tokens converts fixed-depth computation
into variable-length computation: the model writes a partial result and attends to it on the next
step, so the scratchpad is working memory living in the KV cache. That framing predicts both when it
helps — serial problems deeper than the layer count — and how it fails, which is that a wrong step
gets conditioned on and errors compound instead of cancelling.

**"Explain GRPO and why it replaced PPO here."**
PPO needs a learned value network to compute advantages, which is a second model of comparable size
and a well-known source of instability. GRPO samples k completions for the same prompt and uses the
group mean reward as the baseline, so the advantage is just the standardised reward within the group
— no value network, roughly half the memory. It's from DeepSeekMath in 2024, not from R1, which
people frequently get wrong. The catch is that a group where every completion gets the same reward
has zero advantage and contributes nothing, so on problems that are too easy or too hard you burn
compute for no gradient. I measured that fraction across difficulties and built a curriculum to keep
groups mixed.

**"What's the most interesting thing you observed?"**
Response length grew during RL with no length term anywhere in the reward function. Mean completion
went from about 40 tokens to about 95 over a thousand steps, purely because longer reasoning was
more often correct and correctness was what I rewarded. That's the R1-Zero observation, and seeing it
on my own model at three million parameters made the point that it isn't a large-scale emergent
mystery — it's what happens when you optimise for a verifiable outcome and the policy discovers that
more intermediate computation pays.

**"How do you know the RL actually created capability rather than sharpening it?"**
pass@k. If RL only concentrates probability on reasoning the model could already produce, then it
wins at k=1 and the gap closes as k grows, because the base model reaches the same answers given
enough samples — that's selection. If pass@64 improves too, something new was found. I measured both
models at k = 1, 4, 16 and 64 on a held-out set harder than anything in training. It's the sharpest
open question in the area right now and I'd give my numbers with the honest caveat that a 3.4M model
on synthetic puzzles can't settle the general case — but knowing which measurement decides it is the
point.

**"When can you not use RLVR?"**
When you can't write the verifier. RLVR needs a program that grades the output, which covers math,
code with unit tests, and structured tasks with checkable outcomes. For anything where the objective
is helpfulness, tone, or judgment there's no such program, and you're back to a learned reward model
and RLHF — with all the reward-hacking exposure that brings. The clean way to say the difference:
RLHF's reward is learned and therefore attackable, RLVR's is computed and therefore only as good as
the code you wrote. Which is still attackable — I hacked my own verifier three different ways
deliberately before hardening it.
