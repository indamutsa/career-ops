Tracking & orchestration MLflow, Kubeflow, Airflow, DVC. The unglamorous layer that answers one question: can you rebuild this exact model six months from now, and prove which data made it? If you cannot, you cannot debug it, audit it, or safely roll back to it.

The distinction interviewers probe

Airflow orchestrates tasks; Kubeflow orchestrates containers on Kubernetes. If your steps are SQL and Python against existing infrastructure, Airflow is simpler and you should not add Kubernetes to your problem list. If steps need different images, different hardware, and reproducible isolation — the usual shape of training — Kubeflow earns its complexity. Many teams run Airflow as the scheduler that triggers Kubeflow pipelines, and that is a perfectly good answer.

The terms

Run vs experiment basic

A run is one execution with its params, metrics and artifacts. An experiment groups runs that answer the same question.

Log the git SHA, the data version and the environment on every run, or the record is decoration rather than reproducibility.

Model registry mid

A versioned store of model artifacts with stages (staging, production, archived), lineage back to the producing run, and an approval trail.

It creates the deployment boundary: serving pulls "the production version of fraud-scorer", so promoting a model is a registry transition, not a redeploy — and a rollback is the same transition backwards.

Reproducibility senior

Same code + same data + same environment + same seed → same model.

All four are required and the middle two are usually missing. "Same data" means a snapshot or a time-bounded query, not "select * from transactions", which returns something different every day.

Lineage mid

The traceable chain: raw source → transformation → feature → training run → model version → prediction.

What lets you answer "which models used the field that was wrong?" during an incident, and what regulated industries require you to produce on request.

Pipeline caching mid

Skipping a step whose inputs are unchanged, keyed by a hash of code plus inputs.

Turns a six-hour retrain into a twenty-minute iteration when only the last step changed — the difference between experimenting daily and experimenting weekly.

Idempotent, backfillable DAG senior

Every task is parameterised by an execution date and writes to a partition determined by it, so re-running any day produces the same result.

The most common Airflow mistake is a task that reads "the last 7 days" from now() instead of from the execution date. It works on schedule and produces silently wrong results on every backfill — the same event-time-versus-processing-time confusion as module 50, in a different costume.

Questions

MIDA model in production is behaving oddly. Walk me through investigating it.
Establish what is actually deployed, reproduce it, then bisect: is the input different, is the model different, or is the world different? Reproducibility infrastructure is what makes those three separable — without it you are guessing.

1 — Identify the artifact. Which registry version is serving, which run produced it, which commit and which data snapshot that run used. If this takes more than a minute, that is the first finding of the investigation.

2 — Reproduce the prediction. Take a specific bad prediction, pull its logged feature vector, and re-run it locally against the same artifact. If you get a different score, the problem is in serving — wrong version, different preprocessing, a runtime difference. If you get the same score, the model is doing what it was trained to do and the problem is upstream.

3 — Compare inputs. Diff the serving feature distribution against training (module 54). A step change points at a deployment or an upstream schema change; a gradual drift points at the world moving. The shape of the change tells you which, and that distinction determines the fix.

4 — Check what changed and when. Correlate the onset against the deploy log, the upstream release calendar, and the pipeline run history. Most incidents have a cause with a timestamp.

5 — Mitigate, then fix. Roll back to the previous registry version first — restore service, then diagnose at leisure. A rollback you can perform in one command is worth more during an incident than any amount of dashboards.

What makes all of this possible: logged feature vectors per prediction, model version stamped on every response, immutable artifacts in a registry, and pipeline run history. Each is cheap to add before an incident and impossible to add during one.

SENIORWhat does "reproducible" really require?
Pinned code, pinned data, pinned environment, and controlled non-determinism — and a bit-identical rebuild is often not achievable, so the honest target is a model that is statistically equivalent and fully traceable.

Code is the easy one: a git SHA, including the pipeline definition, and no uncommitted changes at run time (fail the run if the tree is dirty).

Data is where it usually fails. "The transactions table" is not a version. You need an immutable snapshot, a time-bounded query with an as-of clause, or a content hash — DVC and table formats like Delta or Iceberg exist to give you exactly this. Without it, re-running the same code next month trains on a different dataset and you cannot tell whether a metric change came from your change or from the data.

Environment: a container image by digest, not by tag — :latest is the enemy of reproducibility, and so is an unpinned transitive dependency. Also the hardware, since GPU non-determinism and different reduction orders change results at the last digits.

Non-determinism: seeds for every RNG (Python, NumPy, the framework), and deterministic algorithm flags where the framework offers them. Note that determinism has a real performance cost — cuDNN's deterministic kernels are slower — so it is a deliberate trade, not a free setting.

The honest position I would state: full bit-identity is expensive and often not worth it. What you actually need is (a) the ability to rebuild a statistically equivalent model, and (b) complete traceability from a prediction back to the exact inputs and artifacts that produced it. The second is the auditable requirement and the one that saves you in an incident; the first is what lets you continue the work. I would invest in traceability first and buy determinism only where regulation or debugging demands it.

MIDHow would you structure a retraining pipeline?
A DAG whose steps are validate data → build features point-in-time → train → evaluate against the incumbent on a temporal holdout → gate → register → deploy behind a canary. The gate is the important part: automation without an automatic stop is a liability.

The steps, and what each is allowed to reject:

  • Data validation. Row counts, null rates, schema, label distribution. Fails the run before wasting the training compute — and stops garbage from silently becoming a model.
  • Feature build with a point-in-time join (module 51), from the same definitions serving uses.
  • Train, logging params, metrics, the data version and the environment to the tracking server.
  • Evaluate on a temporal holdout — the most recent period, never a random split — and on slices that matter: by segment, by amount band, by channel. An aggregate improvement that hides a regression on a key segment must fail the gate.
  • Gate: new model must beat the incumbent on the primary metric by a meaningful margin, regress on no critical slice, and pass latency and size checks. If any fails, stop and alert. No auto-promotion on a marginal win.
  • Register and deploy as a canary (module 53), with automatic rollback on the guard metrics.

On the trigger: scheduled retraining is simple and predictable; drift- or performance-triggered retraining is more responsive but risks retraining on a bad week. I would run a schedule as the baseline with a drift trigger able to pull it forward, and I would require the same gate either way.

The failure mode to name: a feedback loop. If the model's own decisions filter which labels you observe — you only learn the outcome of transactions you approved — then retraining on that data narrows the model's world every cycle. The standard mitigation is a small randomised holdout that bypasses the model, so you keep observing the counterfactual. It costs real money in fraud losses and it is what stops the pipeline degrading in a way no metric can see.
