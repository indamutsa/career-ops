Part C · Deep learning · Module 34

Reinforcement learning Do not skim this one. Every modern LLM is post-trained with RL — RLHF, then DPO, then RLVR and GRPO. Module 44 assumes you know what a policy, an advantage, and a KL penalty are. This is where you learn them, in a setting you already own: the fraud decision from modules 12 and 25. Then, once the machinery is solid, the page pivots to the domain that is the actual reason you need any of this — language models.

What makes RL a different problem

SupervisedReinforcement
SignalThe correct answer, per exampleA scalar reward — how good, not what was right
DataFixed, given, i.i.d.Generated by the agent's own actions
Feedback timingImmediateOften delayed by many steps
Effect of the modelNone on the dataThe policy determines what data exists
The analogy

Supervised learning is learning chess from an annotated book: every position comes with the grandmaster's move. RL is learning chess by playing, being told only "you lost" forty moves later, and having to work out which of those forty moves was the mistake.

That last part is the credit assignment problem, and it is the whole difficulty of the field.

The third row of that table is the one that bites in practice. Because the policy generates its own data, RL training is a feedback loop — a bad policy explores badly, collects bad data, and gets worse. Nothing in supervised learning behaves like this, and it is why RL is unstable in ways that surprise people arriving from the supervised world.

The fraud decision as a decision process

WhatA Markov decision process (MDP) is the formal frame for sequential decisions: a state, a set of actions, a reward for each state–action pair, and — when decisions chain together — a rule for how one state leads to the next.
WhyModules 12 and 25 already gave you a state (a fraud probability), a set of actions (allow / review / block) and a cost matrix. RL is what you get when you stop hand- picking a threshold and instead let an agent learn the action that maximises reward.
Where in MLAny system that repeatedly chooses an action under uncertainty and only later finds out how it paid off: fraud triage, ad bidding, recommendation, robotics, and — from 34.9 onward — next-token generation.

Module 12.1 gave you naive action bands from the fraud probability alone: block above 0.9, review between 0.3 and 0.9, allow below 0.3. Module 25.3 then derived a cost-optimal threshold from the actual cost matrix — a missed fraud costs €200, a false alarm costs €2 of analyst time and customer friction — and that threshold came out near 0.01, far below the naive 0.3 cut-off. RL is the framework that makes that second calculation the whole policy, for every action, not just a single yes/no threshold. Here is the MDP, term by term, with the fraud numbers already in it:

MDP termWhat it is in generalWhat it is for fraud triage
State sEverything the agent is allowed to see before deciding The transaction's fraud probability p from the module 12 model, plus its features
Action aOne choice from a fixed set {allow, review, block}
Reward R(s,a)A scalar telling the agent how that choice turned outMinus the module 25 cost of that action, given whether the transaction was actually fraud or legitimate
EpisodeOne self-contained run, start to endOne transaction: state arrives, action is taken, true label resolves, reward is paid, episode ends

Build the reward directly from the €200/€2 cost matrix. Allow pays the full €200 loss if the transaction turns out to be fraud, and costs nothing if it was legitimate. Block always spends €2 of friction — a legitimate customer who gets blocked is annoyed, and even a genuine fraud attempt costs a little analyst overhead to close out — but if the transaction really was fraud, it avoids the €200 loss. Review spends the same €2 of analyst time regardless of outcome, and — because a human is now looking, not a fixed rule — catches only roughly half of the fraud that reaches it, avoiding half of the €200 loss on average. That "half" is a deliberately concrete stand-in for "review is imperfect but better than nothing"; a real system would measure its own analyst catch-rate.

ActionReward if fraudReward if legitimate
allow−200 (the full loss)0 (no cost)
review+98  (½×200 loss avoided − €2 analyst cost) −2 (analyst time spent on a transaction that needed none)
block+198  (200 loss avoided − €2 friction) −2 (false-alarm friction cost)
Read the table as a policy problem, not a lookup table

Nobody hands the agent this table at run time — it only ever sees p, takes an action, and is told a reward. Learning which action is best for which p, purely from that reward signal, is the entire content of this module.

Interview takeawayAn MDP is a cost matrix (state, action, reward) that an agent has to learn to act on, rather than one you hand-derive once and hard-code as a threshold.

The policy π, and exploration vs exploitation

state (fraud probability p) → action set {allow, review, block} → a rule for choosing among them → policy π
WhatThe policy π is the thing being learned: a mapping from state to action, usually written as a probability the agent assigns to each action in that state.
WhyA fixed threshold rule (module 12/25) is a policy with probability 1 on one action and 0 on the others. RL generalises that to a policy the agent adjusts from experience, and — while training — one that is deliberately not fully certain.
Where in MLEvery RL algorithm in 34.7 is a different way of improving π. For an LLM (34.9), the policy is the model: state = tokens so far, action = the next token.

Write the fraud policy as π(a | s) — the probability of taking action a given state s. Early in training, before the agent has learned anything, a reasonable starting policy for a borderline transaction (say p around 0.5) might spread its probability across all three actions rather than commit:

π(allow | s) = 0.30    π(review | s) = 0.50    π(block | s) = 0.20a deliberately uncertain policy, before training has told it which action pays best at this p
Exploration vs exploitation

Always taking the action the agent currently believes is best (exploit) is your regular restaurant: reliable, but you never learn whether the new place two doors down is better. Occasionally trying an action you are not sure about (explore) is ordering something new — sometimes it is worse, but it is the only way to find out. A fraud agent that always allows every transaction below 0.488 will never learn what would have happened had it reviewed one instead; it needs some exploration to discover that review's expected reward at that p beats allow's.

Section 34.6 will compute exactly which action is best at p ≈ 0.488, and 34.8 will show the concrete probabilities π(block | s) takes as training moves toward that answer.

Interview takeawayA policy is a distribution over actions per state, and deliberately keeping it non-degenerate during training (exploration) is what lets the agent ever discover an action it is not already taking.

Return, discount, and the value functions V and Q

WhatReturn is the total reward an episode pays out, with rewards further in the future multiplied by a discount factor γ < 1 so the sum stays meaningful. V(s) is the expected return from a state under the current policy; Q(s,a) is the expected return from taking a specific action in that state, then following the policy after.
WhyYou cannot compare "allow" and "block" by their reward alone once decisions chain together — you need the expected total payoff each one leads to, not just its immediate number.
Where in MLEvery value-based and actor–critic algorithm in 34.7 is built on estimating V or Q from data.

Our fraud episode is deliberately the simplest case: one transaction, one action, the true label resolves immediately, episode over. There is no "next state" inside the episode, so before adding anything new, note what that simplification buys: Q(s,a) = R(s,a) exactly — the expected return from taking action a is just its expected immediate reward, because there is nothing left to follow. This is not a separate rule; it is the general recursive definition of Q with a zero contribution from "what comes after," because there is no after.

?Where discount γ actually earns its keep

Real fraud systems are not always this clean. A transaction that was allowed can turn into a confirmed chargeback weeks later — a delayed reward, several steps after the decision that caused it. Suppose a review decision today sometimes triggers a follow-up investigation three transactions later on the same account, worth an extra +50 in avoided-loss reward if it catches something the original review missed. With discount γ = 0.9 per step, that future reward is worth, from today's point of view:

discounted value = γ³ × 50
γ³ = 0.9 × 0.9 × 0.9 = 0.729
discounted value = 0.729 × 50 = 36.45
A reward three steps away is worth 36.45, not the full 50 — the agent should still prefer a sure, smaller reward now over a heavily discounted, distant one, unless the distant one is large enough to outweigh the discount.

γ close to 1 makes the agent patient (it plans far ahead); γ close to 0 makes it myopic (only the next reward matters). Our worked example below stays inside one episode, where this never bites — but Bellman's equation in 34.5 is written for the general, multi-step case on purpose.

p = 0.488  —  module 12.9's flagged transaction, P(fraud | flagged) ≈ 0.488
Q(s, allow) = p×(−200) + (1−p)×0
= 0.488×(−200) = −97.6
Q(s, block) = p×(198) + (1−p)×(−2)
= 0.488×198 + 0.512×(−2) = 96.624 − 1.024 = 95.6
Q(s, review) = p×(98) + (1−p)×(−2)
= 0.488×98 + 0.512×(−2) = 47.824 − 1.024 = 46.8
Block has the highest expected reward at this p — even though module 12's naive bands (review between 0.3 and 0.9) would have routed this exact transaction to review. Weighing the actual €200/€2 asymmetry, rather than a hand-picked band, changes the answer.
what each symbol is pthe transaction's fraud probability — the state Q(s,a)expected reward of taking action a in state s (no future step to add, per above) 0.488, 0.512P(fraud | flagged) and its complement, from module 12.9

The value of the state, V(s), is the expected return under whichever policy the agent is actually following. For a policy that has converged to taking the best action, V(s) = maxa Q(s,a) — here, V(s) = Q(s, block) = 95.6. That number is what 34.6's advantage calculation subtracts from.

Interview takeawayV is "how good is this state under my policy"; Q is "how good is this specific action from this state." When an episode ends immediately after one action, Q reduces to the expected immediate reward — the general definition still holds, there is just nothing left to discount.

The Bellman equation

WhatValue decomposes recursively: the value of being in a state now equals the immediate reward plus the discounted value of whatever state comes next.
WhyIt turns "compute the value of every possible future" — intractable — into a one-step relationship you can estimate and update from data.
Where in MLEvery value-based algorithm (Q-learning, DQN, and their descendants) is some way of turning this identity into an update rule.
V(s) = E[ R(s,a) + γ·V(s′) ]s′ is the state one step after s; the whole return is the immediate reward plus the (discounted) value of everything that follows

In our one-decision fraud episode, s′ is terminal — the episode is over once the reward is paid, so V(s′) = 0 and Bellman's equation collapses to V(s) = E[R(s,a)], exactly the calculation in 34.4. The multi-step version earns its keep the moment an account is monitored across several transactions: the value of reviewing this transaction then includes the discounted value of whatever happens on the next one, recursively, all the way to the end of the account's history.

Interview takeawaySay it in one line: "now's value is what you get right now, plus a discounted share of what you get next" — and know that every value-based method is a way of enforcing that identity from sampled data.

The advantage function A(s,a)

Q(s,a) (34.4) → subtract V(s) (34.4) → remove "is this state good" → leave "was this action good" → advantage A(s,a)
WhatA(s,a) = Q(s,a) − V(s): how much better (or worse) a specific action is than the state's average, under the current policy.
WhyQ(s,a) mixes two things: "is this a promising state at all" and "was this particular action a good choice." Subtracting V(s) removes the first and leaves only the second — which is what you actually want a gradient to push on, and it sharply lowers gradient variance.
Where in MLThe core quantity in policy-gradient methods, including PPO (34.8) and, in simplified form, GRPO (34.9).
V(s) = 95.6  —  from 34.4: the value of the best action, block
A(s, block) = Q(s, block) − V(s) = 95.6 − 95.6 = 0
A(s, review) = Q(s, review) − V(s) = 46.8 − 95.6 = −48.8
A(s, allow) = Q(s, allow) − V(s) = −97.6 − 95.6 = −193.2
A(s, block) − A(s, allow) = 0 − (−193.2) = 193.2
The best action always has advantage exactly 0 by construction — it defines V(s). Every other action's advantage says precisely how many expected euros worse it is. The gap between block and allow, 193.2, is the size of the mistake a policy that still allows this transaction is making.
what each symbol is A(s,a)how much better action a is than the state's average return 0the advantage of whichever action the value V(s) itself is built from −193.2expected euros lost, in this state, by allowing instead of blocking
∇J = E[ ∇log π(a|s) · A(s,a) ]the policy gradient: push up the log-probability of actions with positive advantage, push down the ones with negative advantage — for this transaction, push π(allow|s) down hard (A = −193.2) and π(review|s) down more gently (A = −48.8)
Interview takeawayAdvantage answers "was this action a good choice," not "was this a good state" — and every policy-gradient method is pushing probability mass toward positive-advantage actions using exactly this quantity.

On-policy vs off-policy, and the algorithm families

On-policy mid

Learns only from data the current policy generated. REINFORCE and PPO are on-policy: once the policy updates, yesterday's transactions were labelled by a policy that no longer exists, so they are discarded.

Throws data away after one update — costly, but keeps the value/advantage estimates honest for the policy actually being evaluated.

Off-policy mid

Can learn from data any policy generated. Q-learning and DQN are off-policy: a replay buffer of old fraud decisions, made under an older policy, is still valid training data for today's Q-estimate.

Far more sample-efficient, but less stable — the data was not generated by the policy you are currently evaluating, so the estimate is an extrapolation.

FamilyLearnsRepresentativesCharacter
Value-basedQ, then act greedilyQ-learning, DQN, RainbowSample- efficient, off-policy, awkward for continuous actions
Policy-gradientπ directlyREINFORCE, TRPO, PPOHandles continuous and stochastic policies, high variance, on-policy
Actor–criticBothA2C/A3C, SAC, PPOThe critic reduces the actor's variance — the practical default
Model-basedThe environment itselfDyna, MuZero, DreamerVery sample-efficient; a wrong model is confidently wrong

Our fraud policy has three discrete actions, which value-based methods (learn Q(s,a) for each of the three, act greedily) handle comfortably — argmax over three numbers is trivial. That is exactly why value-based methods struggle for an LLM: the "action space" is the vocabulary, 100k or more discrete choices per step, and a stochastic policy is required for sampling. That mismatch is why LLM post-training is policy-gradient, not value-based — the thread 34.9 picks back up.

DQN's two stabilisers, by name

Worth remembering because they show what breaks when a neural network meets the Bellman update. The replay buffer breaks the temporal correlation between consecutive samples, restoring something closer to i.i.d. The target network — a frozen copy of Q updated periodically — stops the network chasing its own moving prediction. Without either, training diverges.

Interview takeawayOff-policy reuses old data but estimates a moving target; on-policy discards data but estimates the policy you actually have. The action space's shape (few discrete actions vs. a huge vocabulary) usually decides the family for you.

PPO: the clipped objective

WhatPPO bounds how far one gradient update can move the policy, by flattening the objective once the new/old probability ratio for an action leaves a band around 1.
WhyA policy-gradient update is only valid locally, near the policy that generated the data. A single large step can move the policy somewhere the advantage estimate says nothing meaningful — and because RL generates its own data (34.1), a broken policy now collects broken data with no way back.
Where in MLThe training loop behind PPO-based RLHF and most production policy-gradient systems.

TRPO fixed the large-step problem with a hard constraint on the KL divergence — a non-negative number measuring how different two probability distributions are, zero only when they are identical — between the old and new policy, solved with second-order machinery: principled, and painful to implement. PPO gets nearly the same effect with a first-order trick: clip the ratio itself.

L = E[ min( r·A , clip(r, 1−ε, 1+ε)·A ) ]  where r = πnew(a|s) / πold(a|s)ε ≈ 0.2 — beyond that ratio, the clipped branch is constant, so its gradient is zero
The analogy

A leash. You can walk in any direction you like, but only so far from where you started before the leash goes taut and pulling harder achieves nothing. The clip is the leash; ε is its length.

Continue the fraud policy from 34.3, where an update raised the probability of blocking a borderline transaction:

πold(block | s) = 0.20    πnew(block | s) = 0.30
r = πnew/πold = 0.30 / 0.20 = 1.5
ε = 0.2  ⇒  band = [1−0.2, 1+0.2] = [0.8, 1.2]
1.5 > 1.2  ⇒  clip(r, 0.8, 1.2) = 1.2
The ratio moved 50% in one update — outside the trust region — so the clip activates. Now use that clipped ratio inside the full objective, for a positive-advantage instance (suppose blocking this particular state carries A = +40, a smaller illustrative advantage than 34.6's, chosen only to show the arithmetic):
r·A = 1.5 × 40 = 60
clip(r)·A = 1.2 × 40 = 48
L = min(60, 48) = 48
Without clipping, the objective would credit the full 60 and keep pushing π(block|s) even higher. Clipping caps the credit at 48 — the gradient beyond r = 1.2 is zero, so this one batch cannot push the policy further in that direction.
what each symbol is rhow much more likely the new policy makes this action than the old policy did clip(r, 1−ε, 1+ε)r, forced into the trust-region band before multiplying by A min(·,·)take whichever term is smaller, so the objective never rewards drifting further than the band allows

The min is the subtle part: it makes the bound pessimistic. For a good action (A > 0, as just shown) it caps the upside so you cannot over-commit off one batch of data. For a bad action (A < 0) it does not cap the correction — increasing the probability of a known-mistake action keeps being penalised without a ceiling, so the policy can always move decisively away from it. Constraint where it protects you, freedom where it saves you.

Interview takeawayCompute the ratio, compare it to the ε-band, and know that the clip only ever removes credit — it never adds gradient signal that was not already there.

The bridge to RLHF

Everything above was taught on a three-action, single-step fraud decision because it makes every number computable by hand. That was never really the destination — the reason this module exists in an ML interview course is that every modern LLM is post-trained with RL, and the mapping from what you just learned onto that setting is the actual payoff. From here the running example switches from fraud triage to language modelling, deliberately: forcing an LLM-specific reward signal into the fraud domain would misrepresent what RLHF is actually optimising, so this table maps the machinery — state, action, reward, value, KL — onto its real target instead.

RL conceptIn RLHF
Policy πThe language model itself
StateThe prompt plus tokens generated so far
ActionThe next token
RewardA learned reward model scoring the finished response — usually one scalar at the end, so the whole sequence shares it
EpisodeOne prompt → one complete response
Value/criticA value head predicting the reward mid-generation
The KL penaltyKL(π ‖ πreference) subtracted from the reward, keeping the policy near the SFT (supervised-fine-tuned) model it started from — module 13.6

Notice the fraud episode and the RLHF episode share the same shape: one state, one chosen action (or sequence of them), one terminal reward, computed exactly the way 34.4–34.6 computed Q, V and A. The difference is scale — a vocabulary instead of three actions, and a learned reward model instead of a hand-derived cost matrix — not the underlying machinery.

The KL penalty is doing two jobs at once and both are worth naming: it is PPO's trust region re-expressed as a reward term (compare 34.8 — bounding how far one update can move the policy), and it is the defence against reward hacking — the reward model is only accurate near the distribution it was trained on, so wandering far from the reference policy means optimising a reward model that no longer knows what it is scoring. The fraud analogue: a reward model scoring transactions would only be trustworthy near the transactions it saw in training, and a policy free to drift arbitrarily would eventually find the score's blind spots too.

GRPO — the variant behind DeepSeek-R1 — deletes the critic entirely. Sample a group of responses to the same prompt, and use the group's mean reward as the baseline: advantage becomes "how much better than my siblings was this answer." That halves the memory (no separate value network) and works well when the reward is verifiable — a maths answer that is right or wrong — which is what RLVR means. Detail in module 44.

Questions

BASICHow does RL differ from supervised learning?
Supervised learning is told the right answer for each example. RL is told only how good an outcome was, often long after the decisions that caused it, and it generates its own training data by acting.

Three differences that each cause a distinct problem:

  • Evaluative, not instructive feedback. A reward number does not tell you which action to have taken instead — the fraud reward table only tells you what block did pay off, not what allow would have paid. You must infer that by trying alternatives or, as in 34.4, computing every action's expected value directly.
  • Delayed reward → credit assignment. A chargeback confirming fraud weeks after the "allow" decision must be attributed back to that one choice. Discounting (34.4) and advantage estimation (34.6) are the machinery for doing that.
  • The data distribution depends on the policy. This breaks the i.i.d. assumption everything in module 20 rests on, and creates a feedback loop where a bad policy collects bad data and degrades further. It is why RL is unstable in ways supervised learning never is.

The practical consequence: RL is orders of magnitude less sample-efficient. If you can obtain labels, supervise. RL earns its cost when the desired behaviour is easy to judge and hard to demonstrate — which is exactly why it is used for LLM alignment. Nobody can write the ideal response to every prompt, but people can reliably say which of two responses is better.

MIDValue-based or policy-gradient — how do you choose?
Value-based when actions are discrete and samples are expensive; policy-gradient when the action space is continuous or the policy must be stochastic. In practice most systems are actor–critic and use both.

Value-based learns Q(s,a) and acts greedily — exactly what 34.4's fraud table does for three actions. Off-policy, so it can reuse a replay buffer of old transactions and is far more sample-efficient. But greedy action selection needs an argmax over actions, which is intractable for continuous control, and the learned policy is deterministic.

Policy-gradient optimises π directly, so continuous actions are natural and a stochastic policy comes for free — which matters in partially observable settings and in games where being predictable loses. The cost is high variance and on-policy sample inefficiency.

Actor–critic is the synthesis: the actor is the policy, the critic estimates value and supplies the advantage (34.6), which cuts the actor's gradient variance sharply. PPO and SAC are both in this family and cover most of what people actually deploy.

For LLMs the choice is forced. The action space is the vocabulary — 100k+ discrete actions per step — and you need a stochastic policy for sampling. Q-learning over that is hopeless, so post-training is policy-gradient, i.e. PPO, or a method like DPO that sidesteps the RL loop altogether.

SENIORWhat exactly does PPO's clipping do, and why is it needed?
It bounds how far one update can move the policy, by flattening the objective once the new/old probability ratio leaves [1−ε, 1+ε]. Beyond that the gradient is zero, so a single batch cannot destroy the policy.

Why a bound is needed at all: the policy gradient is valid only locally, near the policy that generated the data. A large step lands somewhere the estimate says nothing about — and unlike supervised learning there is no recovery, because the damaged policy now collects the data for the next update. Policy collapse in RL is often unrecoverable.

What TRPO did: impose a hard KL constraint and solve the constrained problem properly — conjugate gradient, Fisher-vector products, a line search. Principled, and painful to implement and scale.

What PPO does instead: take the ratio r = πnew(a|s) / πold(a|s) and optimise min(r·A, clip(r,1−ε,1+ε)·A). 34.8 worked this arithmetic for r = 1.5, A = 40: unclipped credit would be 60, clipped credit is 48, and the objective takes the smaller value. Once r drifts outside the band, the clipped branch is constant in the parameters, so its gradient is zero and there is no incentive to push further. First-order, a few lines of code, and it enables several epochs of updates on the same batch — which is where the sample-efficiency gain over vanilla policy gradient comes from.

The min asymmetry is the detail that shows understanding. For A > 0 the upside is capped, so you cannot over-exploit a single good sample. For A < 0 the correction is not capped — the policy can always move decisively away from a bad action. Cautious about good news, unconstrained about bad news.

The honest caveat: clipping bounds the ratio per sample, not the KL over the batch, so it is a heuristic rather than a guarantee — implementations still monitor KL and often add an explicit penalty or early-stop. And the well-known reproducibility work (Engstrom et al.) found a large share of PPO's advantage over TRPO came from implementation details — advantage normalisation, value clipping, orthogonal init, learning-rate annealing — rather than from the clipped objective itself. Knowing that is the difference between having read the paper and having run it.

SENIORWhy is there a KL penalty in RLHF?
Because the reward model is a learned approximation that is only trustworthy near the distribution it was trained on. The KL term ties the policy to the SFT reference, so it cannot escape into a region where the reward is high and meaningless.

The failure it prevents is reward hacking, and it is empirically dramatic: without the penalty, policies find degenerate outputs — repeated flattering phrases, particular formatting tics, excessive length — that score extremely well and are useless. The reward model never saw such text in its training pairs, so its score there is extrapolation. The fraud analogue from 34.9: a reward model trained on typical transactions would be just as unreliable if a policy drifted into inputs unlike anything it was scored on.

Formally the objective is E[r(x,y)] − β·KL(π ‖ πref). Two readings, both correct:

  • As a trust region — the same job PPO's clipping does (34.8), expressed in the reward instead of the objective, keeping updates in the region where estimates are valid.
  • As a Bayesian prior — the solution to that objective is provably π*(y|x) ∝ πref(y|x)·exp(r/β): the reference policy reweighted by exponentiated reward. β sets how much the reward is allowed to move you off the prior. That identity is also exactly the step DPO inverts to remove the RL loop entirely.

Tuning it is a real trade-off. β too high and the model barely changes from SFT. β too low and it hacks the reward and loses general capability — the "alignment tax" shows up as regressions on unrelated benchmarks. Teams monitor KL during training and treat a sharply rising KL with rising reward as the signature of hacking rather than of progress.

And the limit worth stating: the KL penalty constrains distance, not direction. It cannot fix a reward model that is systematically wrong — if annotators preferred confident answers to correct ones, the policy will learn confidence, staying obediently close to the reference the whole way.

MIDWhat is reward hacking, and how would you detect it?
The agent maximises the stated reward while defeating its purpose. Detect it by watching the gap between the proxy reward and an independent measure of what you actually wanted.

The canonical examples: a boat-racing agent that farms a respawning bonus in a lagoon instead of finishing the race; a robot hand that learns to position itself between the camera and the object so it looks like it grasped it. In LLMs: verbosity, sycophancy, confident hedging, and formatting that reward models happen to favour.

Why it is structural, not a bug. Any reward is a proxy for an unstated true objective, and optimisation pressure finds every place the proxy and the objective diverge. This is Goodhart's law with a gradient behind it — the harder you optimise, the more reliably you end up in the divergence. Even the fraud reward table in 34.2 is a proxy: it is only as good as the €200/€2 estimates behind it, and a policy that found a way to game the review action's assumed 50% catch rate would be hacking exactly this way.

Detection in practice:

  • Track proxy reward against a held-out signal — human eval, a different reward model, a verifiable benchmark. Reward rising while held-out quality flattens or falls is the signature.
  • Watch KL from the reference. Reward and KL climbing together, with the reward's rise steeper, usually means hacking rather than learning.
  • Read the outputs. Genuinely — hacks are typically obvious to a human within a handful of samples and invisible in the metrics.
  • Track cheap correlates like response length, which is the most common LLM reward hack and the easiest to instrument.

Mitigations: the KL penalty; ensembling reward models so a quirk of one is not exploitable; retraining the reward model on samples from the current policy (which is what iterated RLHF does); and where possible using verifiable rewards — for maths or code the answer is checkable, so there is far less to hack. That last point is exactly why RLVR is where the field moved.
