Feature stores One idea, one problem, one animation. The idea is "compute a feature once, serve it to both training and inference". The problem is point-in-time correctness — the most expensive and least visible bug in applied ML, and the reason this component exists at all.

The problem a feature store solves

The analogy

You are marking an exam taken last March, and you want to know how well each student was doing at the time. You open the school system, and it shows you their grades today — including the results of the exam you are marking.

Every model built that way looks brilliant offline and collapses in production. The exam it aced in testing contained the answers.

Offline store basic

The full history of every feature value with the timestamp at which it became known. A warehouse or lakehouse table — big, slow, complete.

Used to build training sets. The timestamp column is the whole point; without it the history is unusable for correct joins.

Online store basic

The latest value of each feature per entity, in a low-latency key-value store — Redis, DynamoDB, Cassandra.

Used at inference: one lookup by card_id, single-digit milliseconds, no computation on the request path.

Point-in-time correctness senior

Joining each training label to the feature values as they were known at that label's timestamp — never the latest value.

Also called an as-of join. Getting it wrong is silent: the model trains on information from the future, offline metrics look excellent, and production performance is far worse with no error anywhere in the pipeline.

Train/serve skew mid

The training feature and the serving feature are computed by different code, and disagree.

Two chefs working from the same recipe written in two languages. The dish is subtly different every time, and nobody can say which one is wrong.

Feature view / entity mid

Feast's vocabulary: an entity is the key you look features up by (card, user, merchant); a feature view is a group of features sharing a source and a freshness policy.

Registering them centrally is what makes features discoverable and reusable across teams, which is the second-order benefit people forget to mention.

Materialisation mid

Pushing computed values from the offline store into the online store on a schedule, or streaming them in continuously.

Introduces a freshness lag. A feature materialised hourly is up to an hour stale at inference — and "transactions in the last hour" computed on hour-old data is a fraud feature that has stopped working. Freshness requirements belong in the design, not in the incident review.

On-demand feature senior

Computed at request time from the request payload plus looked-up values — the ratio of this transaction's amount to the card's 30-day average, say.

Necessary because some features depend on the request itself and cannot be precomputed. Feast expresses them as transformations registered once and executed identically in both paths — which is exactly the skew fix.

See the leak

Questions

SENIORExplain point-in-time correctness. Why is it so easy to get wrong?
Every training row must see only the feature values that existed at that row's event time. It is easy to get wrong because the natural SQL join — join the label table to the feature table on the entity key — silently gives you the current value, and nothing about the result looks broken.

The concrete failure. Label: transaction on 3 March, flagged fraudulent. Feature: card_chargeback_count. The naive join returns today's value, which includes the chargeback raised because of that very transaction. The model learns "cards with chargebacks are fraudulent", which is true, useless, and unavailable at decision time. Offline AUC 0.99; production AUC 0.71.

Why it hides so well: there is no error, no null, no type mismatch. The only symptom is that the model is too good — and "too good" is celebrated rather than investigated. A random train/test split does not catch it, because the leak is present on both sides.

What the correct join actually is: for each (entity, event_timestamp) in the label set, take the most recent feature row where feature_timestamp ≤ event_timestamp — and additionally where that value was available by then, which is a second, stricter condition. A feature computed by a nightly batch at 02:00 is not available to a 23:00 transaction even though its timestamp precedes it. Feast models this as an event timestamp plus a created timestamp, and mature pipelines subtract an explicit availability delay.

How I would detect an existing leak: split by time, not at random, and compare — a large gap between a random split and a temporal split is the signature. Then rank feature importances and interrogate the top ones one at a time with the question "could this value have been known before the event?". Anything derived from an outcome, an investigation, or a downstream process is guilty until proven otherwise, and this is the same taxonomy as module 20's leakage section, just with timestamps attached.

MIDDo you actually need a feature store?
You need the properties — point-in-time correct training sets, a low-latency online lookup, and one definition shared by both paths. Whether you need Feast or a hundred lines of your own depends on how many models and teams share features.

When it is overkill: one model, one team, batch scoring. A versioned SQL query plus a well-written as-of join is simpler, and simpler is better. Adopting a feature store to solve a problem you do not have is a genuine cost — a new service, a new failure mode, a new deployment.

When it starts paying:

  • Several models sharing features. Without a registry, four teams write four slightly different versions of "card transaction count, 7 days", and they disagree.
  • Real-time serving. Now you genuinely need an online store and a materialisation path, and you have to keep them consistent.
  • Skew has already bitten you. The store's real product is a single definition executed in both paths.
  • Compliance. Feature lineage — this prediction used these values as of this time — is an auditable artifact you would otherwise have to build.

My default answer is to build the properties first with plain tooling and adopt a store when the second or third model arrives. What I would not do is skip point-in-time correctness on the grounds that there is no feature store — that is the property that matters, and it is available to anyone willing to write the as-of join carefully.

SENIORHow do you eliminate train/serve skew?
One definition, executed by one implementation, in both paths — and then verify it empirically by logging what was actually served and comparing it to what training computed.

Where skew comes from, and each has a different fix: two implementations (pandas for training, Java for serving) that drift apart; different data sources (warehouse vs online store) with different freshness or completeness; different handling of missing values, where training drops nulls and serving imputes; and time-window definitions that differ by a boundary condition — inclusive versus exclusive, or event time versus arrival time.

The structural fixes, in order of strength:

  • Log the served features. The strongest fix, and the one I would do first: write the exact feature vector used for each prediction, and train on those logs. Then skew is impossible by construction, because training data is production data.
  • One implementation. A single transformation, registered once, invoked by both paths — Feast's on-demand transformations, or your own shared library.
  • Bundle preprocessing into the model artifact, so scaling and encoding travel with the weights and cannot be reimplemented differently at serving time.
  • Shadow comparison. Recompute the training-path features for live traffic and assert they match the served ones, within tolerance. This is the test that catches drift between the two before it reaches a model.

And a monitoring backstop: compare the distribution of features at serving time against the training distribution (module 54). Skew shows up as a distribution difference that appeared at a deployment boundary rather than gradually — the shape of the change tells you whether you are looking at skew or at genuine drift.
