Part D · Transformers & GPT · Module 46

LLM systems The model is one component. RAG, agents, evaluation and guardrails are the system around it — and this is where an applied research engineer is judged, because almost every real failure lives here rather than in the weights.

RAG

The analogy

A closed-book exam versus an open-book one. The base model sat the closed-book exam months ago and answers from memory — confidently, including the bits it half-remembers. RAG hands it the textbook open at the right page and says "answer from this".

Which reframes the whole problem: most RAG failures are retrieval failures, not generation failures. If the right page was never handed over, no amount of prompt engineering rescues the answer.

Chunking mid

Splitting documents into retrievable units — typically a few hundred tokens with overlap, ideally along semantic boundaries rather than a fixed character count.

The most under-rated knob in the stack. Chunks too small lose the context that makes them meaningful; too large and the embedding averages several topics into a vector that matches nothing well.

Vector database basic

Stores embeddings and answers approximate-nearest-neighbour queries — HNSW or IVF-PQ indexes rather than an exact scan.

The "approximate" is the point: exact search over 100 M vectors is too slow, and recall@10 of 0.98 at 100× the speed is the right trade. Below a few hundred thousand vectors, a flat index in memory is often the correct engineering answer, not a dedicated database.

Hybrid retrieval senior

Run BM25 (lexical) and dense (semantic) retrieval together and fuse the rankings, usually with reciprocal rank fusion.

They fail in opposite directions: BM25 misses paraphrase, dense misses exact identifiers — error codes, product SKUs, part numbers, surnames. Hybrid beats either alone on essentially every real corpus, and it is the highest-value upgrade to a naive RAG system.

Reranking mid

Retrieve ~100 candidates cheaply with a bi-encoder, then rescore the top of that list with a cross-encoder that reads query and document together (module 42).

Big precision gains at the top of the list, which is all the generator ever sees.

Grounding / attribution senior

Requiring the answer to cite the retrieved chunks it used, and checking that each claim is actually supported by them.

Citations are simultaneously a UX feature, a hallucination reducer, and your evaluation signal — an entailment check — asking a second model whether the cited passage actually implies the claim — is a measurable, automatable faithfulness metric.

Agent mid

An LLM in a loop with tools: it decides an action, the action executes, the result comes back as context, and it decides again until it stops.

Error compounds multiplicatively. At 95 % per-step reliability, a 20-step task succeeds 36 % of the time. This single arithmetic fact explains most agent disappointment.

LLM-as-judge senior

Using a strong model to score outputs against a rubric, instead of exact-match metrics.

Known biases: position (prefers the first option), verbosity (prefers longer answers), and self-preference (prefers its own family's output). Mitigate by randomising order, controlling for length, and calibrating against a few hundred human labels before trusting it.

Questions

MIDDesign a RAG system for a company's internal documentation.
Ingestion with structure-aware chunking → hybrid retrieval → cross-encoder rerank → generation with mandatory citations → an evaluation harness that measures retrieval and generation separately. And permissions enforced at retrieval time, not in the prompt.

Ingestion. Parse each source type properly — a PDF table flattened to prose is unrecoverable downstream. Chunk on structure (headings, sections) rather than a fixed character count, at roughly 300–600 tokens with ~15 % overlap, and prepend the document title and heading path to each chunk so the embedding carries its context. Keep metadata: source, section, last-modified, and the ACL.

Retrieval. BM25 plus dense, fused with reciprocal rank fusion (RRF), which scores each document by 1/(k + its rank) in each list and adds those up, so agreement between the two rankers counts for more than either ranker's raw score; metadata filters for recency and permissions; retrieve ~50 and rerank to the top 5–8 with a cross-encoder. I would start with an off-the-shelf embedding model and only fine-tune it on in-domain pairs once the eval set shows retrieval, not generation, is the bottleneck.

Generation. Chunks in the prompt with explicit ids; instruct the model to answer only from them and to say "not in the documentation" when the context does not support an answer — that refusal path is a feature, and it needs to be tested. Require inline citations.

Evaluation, which is the part that separates a demo from a system. Build a set of a few hundred real questions with known answer locations, then measure the two halves separately: retrieval by recall@k (did the right passage appear anywhere in the top k) and MRR — mean reciprocal rank, the average of 1/(rank of the first correct passage), which rewards putting it first rather than merely somewhere — generation by faithfulness (is each claim entailed by a cited chunk) and answer correctness. Separating them is essential — a bad answer from a good retrieval is a different bug from a bad answer from a bad retrieval, and the fix lives in a different part of the stack.

The two things I would flag early because they sink internal deployments: permissions must be applied as a filter inside the retrieval query — never retrieve then filter, and never rely on the prompt to keep a secret, because the chunk is already in the context window. And freshness: stale documentation is answered confidently and is worse than no answer, so re-index on change and surface last-modified in the citation so the user can judge.

SENIORYour RAG system gives wrong answers. How do you debug it?
Split the pipeline and find the first stage that fails, in order: is the answer in the corpus at all → was it retrieved → did it survive reranking into the prompt → did the model use it correctly. Each stage has a different fix, and guessing wastes weeks.

Stage 0 — is it even there? Grep the corpus. Surprisingly often the document was never ingested, or a parser silently dropped it, or it is inside an image or a table that the extractor mangled. No retrieval change fixes this.

Stage 1 — retrieval. Run the query and inspect the top 50 by hand. If the right chunk is not in there, the problem is retrieval: check chunking first (the answer split across a boundary is the classic cause), then whether the query is lexical in nature — an error code or an ID — which is the case dense-only retrieval loses and BM25 wins.

Stage 2 — reranking. If the chunk was in the 50 but not the final 5, the reranker is the bug. Sometimes it is a domain mismatch; sometimes the chunk is genuinely relevant but phrased unlike the query.

Stage 3 — generation. If the right chunk was in the prompt and the answer is still wrong, look at position (the "lost in the middle" effect from module 45 — put the highest-ranked chunk last, adjacent to the question), at conflicting chunks where two documents disagree and the model silently picks one, and at the model overriding the context with its parametric memory, which is what happens when the retrieved fact contradicts what pretraining taught it.

How I would actually run this: take fifty real failures and label each one by the stage that failed. That histogram tells you where to spend, and it almost never matches the team's intuition — in my experience the answer is usually chunking or the lexical-query gap, both of which are cheap fixes, while the team is discussing fine-tuning the generator.

SENIORHow do you evaluate an LLM feature?
Three layers: deterministic checks for anything checkable, a calibrated LLM-as-judge for what is not, and human review on a sample — all against a fixed, versioned eval set built from real failures, with the production metric as the final arbiter.

Layer 1 — deterministic. Anything with a right answer: does the JSON parse, does the SQL run and return the right rows, do the unit tests pass, is the cited document id real, is the extracted date within range. Cheap, fast, no ambiguity — and it catches most regressions. Run it in CI on every prompt or model change.

Layer 2 — LLM-as-judge for quality dimensions with a written rubric and few-shot examples of each score. Critically, calibrate it: have humans label 200 examples and measure judge–human agreement. If Cohen's κ — an agreement score that subtracts out the agreement two raters would reach by chance, so 0 is no better than guessing and 1 is perfect — is poor, the judge is not measuring what you think and its numbers should not be shipped. Randomise pairwise order, control for length, and prefer a judge from a different model family than the one being judged.

Layer 3 — human review on a stratified sample, especially the tails: the disagreements between layers 1 and 2, and the highest-stakes categories.

The eval set is the real asset. Build it from actual production failures, not from imagination; version it; grow it every time something breaks — every incident should end with a new test case. Keep a held-out slice you never iterate against, or you will overfit your prompts to your own benchmark, which is the LLM-era version of test-set leakage from module 20.

And what ultimately decides: offline metrics are a proxy. The arbiter is the online metric — task completion, escalation rate, thumbs-down rate, human-handoff rate — measured in an A/B test. I would ship behind a flag, compare on the product metric, and treat a divergence between offline and online as information about my eval set rather than noise.

MIDWhy do models hallucinate, and what actually reduces it?
Because the training objective rewards plausible continuations, not true ones — there is no term anywhere in pretraining for "is this factual". Grounding in retrieved sources, making abstention an acceptable output, and checking claims against sources are what measurably help; scolding the model in the prompt does not.

The mechanism. Next-token prediction optimises likelihood under the data distribution. A fluent, well-formed, wrong answer has high likelihood; the model has no representation of "I do not know this" unless something in post-training gave it one. Add that RLHF annotators tend to prefer confident, complete answers over hedged ones, and you have actively trained away the behaviour you want.

What works, in rough order of effect:

  • Retrieval. Put the fact in the context. Recall is easier than recall from weights, and it makes the claim checkable.
  • Attribution. Require citations and verify entailment between each claim and its cited chunk — this converts hallucination from invisible into measurable, which is what makes it fixable.
  • Make abstention legitimate. Train and prompt for "the documents do not cover this", and — the part teams skip — make sure your evaluation rewards it. If your metric penalises "I don't know" the same as a wrong answer, you have told the model to guess.
  • Self-consistency. Sample several answers; disagreement across samples is a usable uncertainty signal for routing to a human.
  • Constrained decoding where the output space is closed — pick from a real catalogue rather than generating a product name.

What does not work: "do not hallucinate" in the system prompt; raising temperature to zero (it makes the same wrong answer deterministic); and asking the model how confident it is, since verbalised confidence is poorly calibrated. Token log-probabilities are a better-calibrated signal than the model's own stated confidence, and they are free.

The honest framing: hallucination is not a bug to be eliminated but a rate to be measured and managed, like a false-positive rate. The engineering question is what rate the product tolerates and what happens on the failures — which is a design decision about the fallback path, not a model decision.

SENIORWhen should you build an agent, and what makes them fail?
Build one when the task genuinely needs dynamic multi-step decisions with tools and the steps cannot be known in advance. They fail because per-step errors compound, and because the loop has no memory of why it already failed.

The compounding arithmetic first, because it should govern the design: at 95 % per-step reliability, 5 steps succeed 77 % of the time, 20 steps 36 %, 50 steps 8 %. Any agent design that does not shorten the chain or add verification per step is fighting an exponential.

The specific failure modes: loops, where the model repeats a failing action because nothing in the context says "you already tried this"; context saturation, where tool outputs fill the window and the original objective drops out; tool misuse from ambiguous schemas; no stopping criterion, so it neither finishes nor gives up; and cost blow-up, since every step is a full inference over a growing context.

What I would do instead, by default: a fixed pipeline with LLM steps inside it. If you know the sequence — retrieve, then extract, then validate, then write — encode it as code and use the model for the parts that need judgement. It is cheaper, debuggable, testable, and it fails predictably. Most "agents" in production are workflows with one or two model-driven branches, and that is the right architecture, not a compromise.

When an agent is genuinely right: the step sequence depends on intermediate results (debugging, research, incident triage), the action space is large and open, and there is a real verifier — tests, a compiler, a schema — so errors are caught rather than propagated. Coding agents work precisely because the test suite is the verifier.

And how I would build it: a small, well-documented set of tools with strict schemas and idempotent operations; a hard step and cost budget; explicit failure memory in the context; checkpointing so a failure resumes rather than restarts; and a human approval gate on anything irreversible. That last one is not a safety nicety — it is what makes it deployable at all, and saying so is what shows you have run one in production rather than in a notebook.
