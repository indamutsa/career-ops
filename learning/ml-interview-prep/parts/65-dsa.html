The coding round The one module with code in it, because a coding round is a coding round. These are not random LeetCode problems — they are the patterns that keep appearing in ML and data-platform interviews, and several of them are literally the feature-engineering code from the rest of this course.

How to run this round

Do not read the solutions first. Open a problem, close the accordion, and write it on paper or in an editor with no autocomplete. Give yourself 20 minutes for the warm-ups and 30 for the rest. Then open the solution and compare — not just whether it works, but whether you stated the complexity and the failure mode before being asked.

Say everything out loud as you go. In a real round, silent correct code scores below narrated nearly-correct code, because the interviewer is grading your reasoning and cannot see it otherwise.

Warm-ups

BASICTop k most frequent elements
Count with a hash map, then either a size-k heap for O(n log k) or bucket-by-count for O(n). Say both; implement the heap unless they push for linear.

Clarify first: can k exceed the number of distinct values? Are ties broken arbitrarily? Does the input fit in memory — because if it is a stream, the honest answer is that exact top-k needs O(distinct) memory and you would reach for Count-Min Sketch or Space-Saving instead.

from collections import Counter
import heapq

def top_k_frequent(nums, k):
    counts = Counter(nums)
    return heapq.nlargest(k, counts, key=counts.get)   # O(n log k)

The linear version, when they ask for better than n log k — counts are bounded by n, so they can index buckets directly:

def top_k_frequent_linear(nums, k):
    counts = Counter(nums)
    buckets = [[] for _ in range(len(nums) + 1)]
    for value, c in counts.items():
        buckets[c].append(value)

    out = []
    for c in range(len(nums), 0, -1):
        for value in buckets[c]:
            out.append(value)
            if len(out) == k:
                return out
    return out

Complexity: heap version O(n log k) time, O(distinct) space. Bucket version O(n) time, O(n) space — the trade you are making is memory for the log factor.

The follow-up that catches people: "now it is a stream of a billion events." Exact top-k is no longer possible in bounded memory. Name Count-Min Sketch, accept the one-sided error, and say what the error bound depends on.

BASICSessionise a user's events by an inactivity gap
Sort by timestamp, sweep once, and start a new session whenever the gap since the previous event exceeds the threshold. It is merge-intervals wearing different clothes.

Clarify: is the input already sorted (it is, if it came from a keyed Kafka partition)? Are timestamps in event time or processing time — because out-of-order events break the single sweep and that is exactly the watermark problem from module 50.

def sessionize(timestamps, gap):
    """timestamps: one user's event times. Returns [(start, end), ...]."""
    if not timestamps:
        return []

    ts = sorted(timestamps)
    sessions = []
    start = prev = ts[0]

    for t in ts[1:]:
        if t - prev > gap:
            sessions.append((start, prev))
            start = t
        prev = t

    sessions.append((start, prev))
    return sessions

Complexity: O(n log n) for the sort, O(n) if the input arrives ordered, O(1) additional space beyond the output.

Trap: forgetting to append the final session after the loop. Write one test with a single event and one with all events inside one session before you say you are done.

MIDLRU cache with O(1) get and put
Hash map plus a doubly linked list. In Python, OrderedDict is exactly that data structure, so use it — and be ready to write the linked list by hand if they ask you to.
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.data = OrderedDict()

    def get(self, key):
        if key not in self.data:
            return -1
        self.data.move_to_end(key)          # mark as most recent
        return self.data[key]

    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = value
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)   # evict least recent

Why the linked list. A plain dict gives O(1) lookup but no notion of order; a list gives order but O(n) removal from the middle. The doubly linked list gives O(1) removal given a node, and the hash map is what hands you the node.

The ML follow-up: "you are caching feature lookups — is LRU the right policy?" Often not. Feature access in fraud is bursty per entity and highly skewed, so LFU or a TTL policy may beat LRU, and correctness matters more than either: a stale cached feature is silent skew. Cache with a TTL shorter than your freshness requirement.

The ones a fraud or streaming shop will actually ask

MIDSliding window maximum in O(n)
A monotonic deque of indices whose values are decreasing. The front is always the window's maximum; each index is pushed and popped at most once, so it is linear.
from collections import deque

def sliding_max(nums, k):
    dq = deque()      # indices; nums[dq] is decreasing
    out = []

    for i, x in enumerate(nums):
        while dq and nums[dq[-1]] <= x:
            dq.pop()                 # x dominates these: they can never be a max again
        dq.append(i)

        if dq[0] <= i - k:
            dq.popleft()             # front has fallen out of the window

        if i >= k - 1:
            out.append(nums[dq[0]])

    return out

The insight to say out loud: if a later element is larger than an earlier one, the earlier one is useless forever — it will leave the window first and it is smaller. That single observation is the whole algorithm.

Complexity: O(n) time (amortised — each index enters and leaves the deque once), O(k) space.

Follow-up: "make it a rolling mean instead." Now a running sum works and is simpler — but mention floating-point drift over a long stream, and that recomputing periodically or using Welford's method avoids it.

MIDVelocity counter — events per key in the last N seconds
A deque of timestamps per key, evicting from the front on every access. This is literally the txn_count_1h feature from the fraud walkthrough, so treat it as a design question as much as a coding one.
from collections import defaultdict, deque

class VelocityCounter:
    """Count events per key within a trailing time window."""

    def __init__(self, window_seconds):
        self.window = window_seconds
        self.events = defaultdict(deque)

    def record(self, key, ts):
        q = self.events[key]
        q.append(ts)
        self._evict(q, ts)

    def count(self, key, ts):
        q = self.events[key]
        self._evict(q, ts)
        return len(q)

    def _evict(self, q, now):
        cutoff = now - self.window
        while q and q[0] <= cutoff:
            q.popleft()

Complexity: amortised O(1) per operation; space O(events currently in window), which is the number you must bound.

The four follow-ups, and they always come:

  • Memory across keys. The dict grows forever — a key seen once is never removed. Add TTL eviction of idle keys, or back it with Redis and let key expiry do the work.
  • Out-of-order events. record assumes monotonic timestamps. Late events need either insertion into a sorted structure or an accepted lateness bound — the watermark trade-off.
  • Exact counts are expensive at scale. Bucketed counters (per-minute buckets summed over the window) trade a little precision for constant memory per key, and that is what most production systems actually run.
  • Point-in-time correctness. When you build training data for this feature, the count must be as of the transaction's own timestamp — not the count today. The same class that serves it should be the one that replays history.
MIDFind fraud rings — accounts connected by shared devices
Union-find over a bipartite account–device graph. Union each account with each device it used; accounts that end up in the same component share a device chain.
class DSU:
    def __init__(self):
        self.parent = {}
        self.size = {}

    def find(self, x):
        self.parent.setdefault(x, x)
        self.size.setdefault(x, 1)

        root = x
        while self.parent[root] != root:
            root = self.parent[root]

        while self.parent[x] != root:            # path compression
            self.parent[x], x = root, self.parent[x]
        return root

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False
        if self.size[ra] < self.size[rb]:        # union by size
            ra, rb = rb, ra
        self.parent[rb] = ra
        self.size[ra] += self.size[rb]
        return True


def rings(logins, min_size=3):
    """logins: [(account_id, device_id), ...] -> components of accounts."""
    dsu = DSU()
    for account, device in logins:
        dsu.union(('a', account), ('d', device))

    groups = {}
    for account, _ in logins:
        groups.setdefault(dsu.find(('a', account)), set()).add(account)

    return [g for g in groups.values() if len(g) >= min_size]

Complexity: effectively O(n·α(n)) — near linear — with path compression and union by size. Say "inverse Ackermann, effectively constant" and move on.

Why namespaced tuples. Account ids and device ids can collide as raw values; tagging them keeps the two node types distinct in one structure. Small detail, and interviewers notice it.

The judgment follow-up: "so is a large component fraud?" No. Shared devices also mean a family, a public terminal, a corporate NAT, or a device-id reset. A big component is a signal — good as a feature (component size, growth rate) and as a review trigger, dangerous as a rule. Saying this unprompted is the difference between a coding answer and an ML answer.

SENIORReservoir sampling — a uniform sample from a stream
Keep the first k. For item i (0-indexed) beyond that, replace a random slot with probability k/(i+1). Every item seen ends up in the sample with equal probability, in one pass, with O(k) memory and no knowledge of the stream length.
import random

def reservoir(stream, k):
    sample = []
    for i, item in enumerate(stream):
        if i < k:
            sample.append(item)
        else:
            j = random.randint(0, i)     # inclusive
            if j < k:
                sample[j] = item
    return sample

The proof sketch they may ask for. By induction: after n items each is held with probability k/n. Item n+1 is taken with probability k/(n+1); an existing item survives if either the new item is rejected, or it is accepted but a different slot is overwritten — which multiplies out to exactly k/(n+1). Being able to sketch this in three sentences is a strong signal.

Where this is not a puzzle. The randomised holdout that fixes the fraud feedback loop is a sampling problem of exactly this shape: choose a small unbiased slice of traffic to approve regardless of score, in one pass, without knowing the day's volume in advance.

Follow-up: "make it weighted." Uniform reservoir sampling does not extend naively. The standard answer is the A-Res algorithm — draw a key u1/w per item and keep the k largest in a heap.

Implement the ML primitive

MIDNumerically stable softmax and cross-entropy
Subtract the row max before exponentiating — it leaves the softmax unchanged algebraically and prevents overflow. And never compute log(softmax) by taking a log of a probability: fold it into log-sum-exp.
import numpy as np

def softmax(z):
    z = z - z.max(axis=-1, keepdims=True)      # shift-invariant, kills overflow
    e = np.exp(z)
    return e / e.sum(axis=-1, keepdims=True)


def cross_entropy(logits, labels):
    """logits: (n, c) raw scores. labels: (n,) integer class indices."""
    z = logits - logits.max(axis=-1, keepdims=True)
    logsumexp = np.log(np.exp(z).sum(axis=-1))
    correct = z[np.arange(len(labels)), labels]
    return float(np.mean(logsumexp - correct))

Why the shift is free. softmax(z + c) = softmax(z) for any constant c, because the constant factors out of numerator and denominator. Choosing c = −max makes the largest exponent exactly 0, so nothing overflows and the largest term is 1.

Why not log(softmax(z)). If a probability underflows to 0, its log is −∞ and the loss is destroyed. Computing logsumexp(z) − zcorrect never forms the small probability at all. This is why every framework has a cross_entropy_with_logits and why passing it softmax output is a classic bug.

Follow-up: "now write the gradient." For cross-entropy over softmax logits it is beautifully simple — softmax(z) − onehot(y), averaged over the batch. If you can state that instantly you have shown you understand why this pairing is used at all.

MIDOne iteration of k-means
Assign every point to its nearest centroid, then move each centroid to the mean of its assigned points. Handle the empty-cluster case, because that is what they are checking.
import numpy as np

def kmeans_step(X, centroids):
    """X: (n, d). centroids: (k, d). Returns (assignments, new_centroids)."""
    # squared distances, (n, k) via broadcasting
    d2 = ((X[:, None, :] - centroids[None, :, :]) ** 2).sum(-1)
    assign = d2.argmin(axis=1)

    new = np.stack([
        X[assign == j].mean(axis=0) if np.any(assign == j) else centroids[j]
        for j in range(len(centroids))
    ])
    return assign, new

Complexity: O(n·k·d) per iteration, and the broadcast above allocates an (n, k, d) array — fine on a whiteboard, wasteful at scale. Mention that ||x−c||² = ||x||² − 2x·c + ||c||² turns it into one matrix multiply, which is what real implementations do.

The three details that earn the point: squared distance (no need for the square root — it does not change the argmin); the empty-cluster branch (otherwise you get NaN and silently lose a cluster); and that this converges to a local optimum, which is why k-means++ initialisation and multiple restarts exist.

SENIORPick the decision threshold that minimises expected cost
Sort by score descending, sweep once accumulating true and false positives, and evaluate the cost at every possible cutoff. This is the threshold-selection step from the fraud walkthrough, and it is a sorting-plus-prefix-sum problem.
import numpy as np

def best_threshold(scores, labels, cost_fp, cost_fn):
    """Flag everything scoring at or above the returned threshold."""
    order = np.argsort(-scores)
    y = labels[order]

    tp = np.cumsum(y)                    # positives caught if we flag the top i+1
    fp = np.cumsum(1 - y)                # legitimate customers wrongly flagged
    fn = y.sum() - tp                    # fraud we let through

    cost = fp * cost_fp + fn * cost_fn
    do_nothing = y.sum() * cost_fn       # the baseline you must beat

    i = int(cost.argmin())
    if cost[i] >= do_nothing:
        return None, float(do_nothing)   # no threshold is worth deploying

    return float(scores[order][i]), float(cost[i])

Complexity: O(n log n) for the sort, O(n) for the sweep. Note that computing a confusion matrix independently at each of n candidate thresholds would be O(n²) — the prefix sum is what makes it tractable, and saying so is the algorithmic content of the answer.

The ML content, which matters more here. The threshold is a business decision, not a model property: cost_fp is the value of a wrongly declined customer (including churn, not just the transaction), cost_fn is the loss on missed fraud. Both are estimates, so I would show the cost curve rather than a single number, and check how flat it is around the optimum — a sharp minimum means the threshold is fragile and will need re-tuning as the base rate drifts.

Two traps. First, the threshold must be chosen on validation data and then held, not re-fit on the test set. Second, this optimises on the score distribution you have — if the live base rate differs from the validation set, the optimal threshold moves, which is why threshold re-calibration belongs in the monitoring loop and not only at training time.

How to talk while you code

The sequence that scores
  1. Restate the problem in one sentence and confirm it. Thirty seconds, and it catches half of all misunderstandings.
  2. Ask about input size, ordering, duplicates, and edge cases — empty, one element, all identical. This is where the interviewer decides whether you write production code or exercises.
  3. State the brute force and its complexity, then say what you will improve and why. Never start typing the optimal solution silently.
  4. Name the pattern — "this is a monotonic deque", "this is union-find". It shows recognition rather than rediscovery.
  5. Write it, narrating the invariant, not the syntax. "The deque holds indices whose values are decreasing" is useful; "now I loop over the array" is not.
  6. Trace one small example by hand before claiming it works, and check the edge cases you named in step 2.
  7. State final complexity, time and space, and one thing you would change for production.
