Inference & efficiency Training happens once; serving happens forever. This is the module an engineer is expected to own, and the one where a candidate who has actually deployed a model is instantly distinguishable from one who has only read papers.

The one distinction everything else hangs off

WhatInference is the process of turning an input prompt into generated output tokens with a trained model.
WhyThe prompt and output use hardware differently, so one undifferentiated latency number hides the actual bottleneck.
UseSeparate prefill from decode whenever you size, profile or optimise an autoregressive serving system.
request arrives → prefill the prompt in parallel → cache its keys and values → decode one token at a time → schedule the next request
Running example · the support assistant

The camera-shop assistant receives a 1,000-token troubleshooting history and produces a 100-token answer. The user experiences time to first token, then the cadence of the remaining tokens. Every technique below improves one of those two phases or lets more such requests share the same GPU.

?FLOPs, bandwidth, HBM and arithmetic intensity

FLOP: one floating-point arithmetic operation. A compute-bound phase waits for arithmetic units to finish.

Memory bandwidth: bytes transferred per second. A bandwidth-bound phase waits for data, even when arithmetic units are available.

HBM: high-bandwidth memory attached to an accelerator. Model weights and the KV cache live there during inference.

Arithmetic intensity: arithmetic operations divided by bytes moved. Prefill reuses weights across many prompt tokens, so it has higher intensity than single-token decode.

The support batch

During decode, producing one new support token requires reading the model weights even though the step performs relatively little arithmetic. Serving several support requests together reuses that weight read across several token computations, increasing throughput at the cost of shared capacity and potentially more queueing latency.

The techniques

WhatInference techniques reduce repeated computation, reduce stored bytes, or schedule more requests onto the same hardware.
WhyPrefill, decode and KV storage stress different resources, so an optimisation must target the actual bottleneck.
ChooseProfile first: use kernels for compute, quantisation for weight traffic, batching for utilisation, and KV techniques for context capacity.
KV cache mid

Store the keys and values already computed for every previous token, so generating token n costs one new K and V rather than recomputing all n.

size = 2 × L × n × dkv × bytes × batch2 for K and V · L layers · n tokens · dkv total head dim · precision

Turns generation from O(n²) into O(n) per token — and it is also the thing that eats your GPU memory. It grows linearly with context and batch size, so it, not the weights, usually caps your batch.

MQA / GQA senior

Multi-Query Attention shares a single K/V head across all query heads; Grouped-Query Attention shares one per group of heads — the middle ground everyone actually ships.

Shrinks the KV cache by the sharing factor. Llama-2-70B uses 8 KV heads for 64 query heads: an 8× smaller cache, and near-identical quality. Bigger batches follow directly.

Continuous batching senior

Instead of running a fixed batch to completion, admit and evict sequences per decoding step as they finish.

Static batching wastes the GPU waiting for the longest sequence in the batch. This is the single biggest throughput win in a real serving stack — often several times, not percent.

PagedAttention senior

Store the KV cache in fixed-size non-contiguous blocks with a lookup table — virtual memory paging, applied to attention.

Naive allocation reserves the maximum possible length per request and wastes most of it, exactly like fixed-partition memory allocation did. Paging cuts that fragmentation to a few percent, and it makes prefix sharing across requests nearly free.

Quantisation mid

Store weights (and sometimes activations and the KV cache) in fewer bits — INT8, INT4, FP8.

Since decode is bandwidth-bound, halving the bytes nearly halves the latency. INT8 is essentially free in quality; INT4 with a good method (GPTQ, AWQ) costs little; below that, quality falls off sharply.

Speculative decoding senior

A small draft model proposes k tokens; the big model verifies all k in one forward pass and accepts the longest correct prefix.

Exploits the fact that verification is parallel while generation is sequential. Output is provably identical to the target model's sampling — it is a latency trick, not an approximation. Typical speedups 2–3×.

FlashAttention senior

Compute attention in tiles inside SRAM without ever materialising the n×n matrix in HBM.

Exact, not approximate — the mathematics is unchanged. It is an IO-aware kernel, and this is the correction to make if an interviewer calls it an approximation.

LoRA / QLoRA mid

Freeze the base weights and train a low-rank update ΔW = BA with rank r ≪ d. QLoRA additionally keeps the frozen base in 4-bit.

Trains <1 % of the parameters, and the adapter is a few MB. At serving time you can hold one base model and hot-swap hundreds of adapters — the reason per-customer fine-tuning is economically viable at all.

Interview takeawayName the limiting resource before the technique; otherwise an optimisation can improve the wrong phase while worsening latency or capacity.

Questions

MIDWhat is the KV cache and why does it matter?
It stores the keys and values of all previous tokens so each new token attends to them without recomputation — turning per-token cost from O(n²) into O(n). It is also the dominant consumer of GPU memory at serving time, so it sets your maximum batch size and therefore your throughput.

Why it is correct to cache. With a causal mask, token i's key and value depend only on tokens ≤ i, so they never change as generation continues. Only the query is new at each step. Without the cache you would recompute the entire prefix's K and V every step — quadratic work for an identical result.

The number that makes it real. Llama-2-13B: 40 layers, 40 heads × 128 dim, fp16. Per token: 2 × 40 × 5120 × 2 bytes = 800 KB. At 4,096 context that is 3.3 GB per sequence. On an 80 GB A100 holding 26 GB of weights, you fit about 16 concurrent sequences — and the model weights were never the constraint. That arithmetic is the whole reason GQA, quantised KV and paging exist.

The consequences worth naming: the cache scales linearly in context length, so long-context serving is a memory problem before it is a compute problem; it makes decode bandwidth-bound, since you re-read the whole cache every step; and it creates the prefix-sharing opportunity — a shared system prompt across users can be computed and stored once, which is frequently the cheapest large win available in a production stack.

SENIORYour 7B model serves 8 requests/second at 2s p99. You need 50 rps at the same latency. What do you do?
Measure first to find out whether I am prefill-bound or decode-bound, then work the free wins in order: continuous batching, GQA/paging, quantisation, speculative decoding — and only add hardware once the software is not leaving 5× on the table.

Step 0 — measure. Split TTFT from TPOT, get the input/output length distribution, and check GPU utilisation. If utilisation is low, this is a batching problem, not a capacity problem, and buying GPUs would be burning money. I would not propose a single change before seeing these numbers.

Then, in cost order:

  • Continuous batching (vLLM / TGI). If the stack is doing static batching, this alone is often 3–5× throughput with no quality change. Highest value, lowest risk.
  • PagedAttention. Recovers the memory lost to over-allocation and enables prefix sharing — bigger batches for free.
  • GQA if the model supports it, or KV-cache quantisation to INT8. A smaller cache is a bigger batch.
  • Weight quantisation to INT8/FP8. Decode is bandwidth-bound, so this cuts latency roughly proportionally. Validate quality on the held-out set — this is the first change that can move the metric.
  • Speculative decoding if p99 latency, not throughput, is the binding constraint. It buys latency, and it costs the extra memory of the draft model.
  • Horizontal scaling last, once per-replica throughput is actually maximised.

The product levers I would put on the table too, because they are often the cheapest of all: cap max output length; cache responses to repeated prompts; route easy requests to a smaller model; and separate the interactive path from a batch path with a much looser SLO. A latency budget is a product decision as much as an engineering one.

What I would explicitly avoid: jumping to a distilled or smaller model first. That is the only option in the list that changes output quality, and I would exhaust the quality-neutral ones before spending accuracy on a problem that is probably a batching bug.

SENIORHow does speculative decoding work, and why is it not an approximation?
A small draft model generates k tokens cheaply; the large model scores all k in a single forward pass; a rejection-sampling rule accepts a prefix and corrects the first rejected token. The acceptance rule is constructed so the output distribution is exactly the large model's.

The mechanism. Decode is bandwidth-bound, so a forward pass over k tokens costs barely more than over one — the weights are loaded once either way. That is the free lunch being exploited: verification is parallel, generation is sequential.

The acceptance rule. For a draft token with draft probability q(x) and target probability p(x), accept with probability min(1, p(x)/q(x)). On rejection, sample the replacement from the normalised residual distribution max(0, p−q). Leviathan et al. prove this yields exactly p — the same theorem structure as rejection sampling. So the output is distributionally identical to running the big model alone; there is no quality/latency trade-off to negotiate, which is unusual and worth saying explicitly.

What governs the speedup: the acceptance rate, which is how well the draft model agrees with the target. A draft from the same family works well; an unrelated one does not. And k has an optimum — too large and you waste compute on tokens that will be rejected. Typical results are 2–3×.

The variants that avoid the second model: Medusa adds extra prediction heads to the target model itself; EAGLE drafts in feature space; n-gram / prompt-lookup decoding drafts by copying from the prompt, which is startlingly effective for summarisation and code editing where output repeats input. All the same theorem, no separate model to host.

When it does not pay: under large batches. The technique trades spare compute for latency, and at high batch sizes there is no spare compute — you are already compute-bound, so the verification pass is no longer nearly free. It is a low-batch, latency-sensitive optimisation.

MIDExplain LoRA. Why does it work?
Freeze W and learn a low-rank update ΔW = BA where B is d×r, A is r×d and r is small. It works because the weight update needed for adaptation has low intrinsic rank, even though the weight matrix does not.

The mechanics. Forward becomes h = Wx + BAx, with B initialised to zero so training starts exactly at the base model. For d = 4096 and r = 8, ΔW would be 16.7 M parameters but BA is 65 K — about 0.4 %. Only A and B get gradients and optimiser state, which is where the memory saving actually comes from: Adam's states are 2× the trainable parameters.

Why low rank is enough. Aghajanyan et al. showed fine-tuning has a low intrinsic dimension — you can reparameterise into a few thousand dimensions and still match full fine-tuning. Adaptation moves the model within a small subspace of behaviours it can already express; it is not learning new capability from scratch. That connects straight back to the elicitation framing in module 44.

The serving property that matters most. BA can be merged into W after training, so there is zero added inference latency — unlike adapter layers, which insert extra computation. Or you keep it unmerged and hot-swap adapters per request against one shared base: a few MB per customer instead of a few GB. That is what makes per-tenant fine-tuning economic.

QLoRA adds 4-bit NF4 quantisation of the frozen base, double quantisation, and paged optimisers — enough to fine-tune a 65 B model on a single 48 GB GPU. The base is quantised; the LoRA weights stay in bf16, so gradient quality is preserved.

The honest limits: LoRA slightly underperforms full fine-tuning when the task genuinely requires new knowledge rather than new behaviour; r and which modules to target (attention projections, or the FFN too) both need tuning; and stacking many adapters degrades unpredictably.

SENIORWhat breaks when you push context from 8K to 1M?
Attention's n² compute, the KV cache's linear memory, positional extrapolation, and — the one people forget — retrieval quality inside the context itself.

Memory. The KV cache is linear in n, so 1 M tokens on a 13 B model is roughly 800 GB per sequence at fp16 — multiple nodes for a single request. This is the binding constraint, and it is why long-context serving relies on GQA, KV quantisation, and eviction schemes like StreamingLLM that keep the attention sinks plus a sliding window.

Compute. Prefill is O(n²d): 1 M tokens is ~15,000× the attention work of 8 K. FlashAttention removes the memory blow-up but not the FLOPs. Chunked prefill and ring attention across devices are the standard responses.

Positions. A model trained at 8 K has never seen position 900,000. RoPE extrapolates badly; position interpolation and YaRN rescale the frequencies so trained positions cover the new range, and both need a fine-tuning stage at the target length. ALiBi extrapolates more gracefully by construction.

Quality — the part that gets skipped. "Lost in the middle" (Liu et al.): accuracy on information placed mid-context is markedly worse than at either end, and the effect persists in models that advertise long context. Needle-in-a-haystack tests pass while multi-hop reasoning over the same context fails, because retrieving one fact is not the same as using many. A 1 M context window is not equivalent to 1 M tokens of usable working memory, and I would benchmark on the real task rather than trusting the advertised number.

So the engineering call: for most applications retrieval into a 32 K window beats stuffing 1 M — cheaper, faster, and often more accurate, because the model attends over relevant content instead of hunting through noise. Long context earns its cost when the input is genuinely irreducible and cross-referential: a whole codebase, a long trial transcript.
