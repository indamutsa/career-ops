Part A · Maths · Module 13

Information theory Module 12 taught a fraud classifier to output a probability. This module asks a narrower question: once you have that probability, and later find out the truth, how do you score how good it was? One fraud classifier, one audited batch of transactions, and four questions built from it — surprise, entropy, cross-entropy, KL divergence — cover your training loss, your evaluation metric, and your production drift alarm.

The problem this was invented to solve

Your fraud classifier from module 12 scores a transaction and outputs P(fraud) = 0.03. Below the review threshold of 0.3, so it is allowed through. A week later the audit team confirms it was fraud. That result should feel like a bigger deal than a transaction the model scored 0.97 — blocked — that also turns out to be fraud. Same true label, very different amount of "I told you so."

The founding idea

Information is surprise. A message that tells you something you already expected carries little. The model expected this transaction was almost certainly fine (97% chance), and it was fraud anyway — that carries a lot of information about how wrong the model was. The model expecting fraud (97% chance) and getting fraud confirms what it already believed — barely any information at all. The rarer the outcome looked, the more informative its occurrence is.

Shannon needed this to answer an engineering question — how few symbols can you send down a wire and still convey a message — but it turns out to answer an ML question just as directly: training a classifier is choosing probabilities that minimise how surprised you are, on average, by the labels you actually see. That average surprise is not a metaphor for your training loss. It is your training loss, and this page derives it in real numbers from the fraud classifier, one piece at a time.

The one example for this module

Everything below is this fraud classifier and its audited transactions. No coin flips, no weather forecasts, no unrelated toy datasets. Section 13.2 scores one transaction. 13.5 scores a small labelled batch. 13.6 onward works from one audited sample of 100 review-band transactions, broken down first as a whole, then by merchant category. Every number that appears later was computed from a number you already saw.

How surprising was this transaction — self-information

WhatTurn one predicted probability into one number: how startling that particular outcome was.
WhyBefore you can average how wrong a model's probabilities were across a whole batch, you need a way to score how wrong a single one was.
Where in MLThe per-example term inside every classification and language-model loss.
?Why the formula is −log p

Three things you would want from a "how surprising was this" score: a certain event (p = 1) should score 0 — no surprise. A near-impossible event (p → 0) should score close to infinity. And the score should fall as p rises — rarer means more surprising. The function −log p satisfies all three (13.11 shows it is the only function that does), so that is the definition: self-information, or surprise, of an outcome with probability p is −log p.

Transaction 1: model said p = 0.03, outcome was fraud
surprise = −log₂(0.03) = 5.06 bits
Transaction 2: model said p = 0.97, outcome was fraud
surprise = −log₂(0.97) = 0.04 bits
Same outcome (fraud) both times. The first transaction is 100+ times more surprising than the second, because the model's own probability said it should be nearly impossible.
what each symbol is pthe model's predicted probability of the outcome that actually happened −log₂ psurprise measured in bits — log base 2, explained next 5.06 bits−log₂(0.03): the model assigned this outcome roughly a 1-in-33 chance
Interview takeawaySurprise is −log p: zero for a certain outcome, large for a rare one, and it is what turns a single prediction into a single loss contribution.

Bits vs nats — the only thing the log base changes

Whatlog₂ measures surprise in bits; ln (natural log) measures it in nats. Same quantity, different ruler.
WhyFrameworks compute in natural log internally, but bits are the easier number to reason about by hand — a bit is one yes/no question.
Where in MLYour training loss is printed in nats; language-model papers often report bits-per-character instead. Convert with 1 nat ≈ 1.443 bits.
5.06 bits × ln(2) = 5.06 × 0.6931 = 3.51 nats
check directly: −ln(0.03) = 3.51 nats
Both routes land on the same number. Bits and nats disagree only in units, the way metres and feet disagree — the underlying surprise did not change.
Interview takeawayIf a reported loss number looks unfamiliar, check whether it is in nats or bits before concluding anything is wrong.

How uncertain is the model about one transaction — entropy

surprise of one outcome → average it over every outcome the distribution allows → entropy of the distribution
WhatThe probability-weighted average surprise of a whole distribution — its built-in, irreducible uncertainty.
WhyBefore judging whether the model's belief matches reality, you need to know how uncertain that belief already is on its own.
Where in MLThe floor on average achievable loss — no model beats the entropy of the true label distribution in expectation.
P = 0.030.97  (model's predicted [fraud, not-fraud] for this transaction)
H(P) = −[0.03 × log₂(0.03) + 0.97 × log₂(0.97)]
= −[0.03×(−5.06) + 0.97×(−0.04)] = −[−0.152 − 0.043]
= 0.194 bits
The model is quite sure about this transaction (97% not-fraud), so its own uncertainty about the outcome is small: 0.194 bits, far below the 1-bit maximum.
what each symbol is H(P)entropy — the expected surprise if you sampled from P itself Pthe model's own predicted distribution for one transaction, written as a two-entry vector
?Where entropy is highest and lowest

A transaction the model is completely sure about (p = 0.001 or p = 0.999) has entropy near 0 — almost no uncertainty to average over. The worst case for a two-outcome distribution is p = 0.5, a genuine coin flip:

H([0.5, 0.5]) = −[0.5×log₂(0.5) + 0.5×log₂(0.5)] = −[0.5×(−1) + 0.5×(−1)] = 1 bit
1 bit is the maximum possible entropy for two outcomes — exactly one yes/no question's worth of uncertainty. Our transaction's 0.194 bits sits far below that, because the model is genuinely confident, not just guessing.
Interview takeawayEntropy is a property of a distribution, not a sample — it says how much uncertainty is baked into the model's belief before you ever check the label.

What training actually pays — cross-entropy

entropy of the model's own belief → now compare that belief against the true label instead → cross-entropy
WhatThe average surprise you actually rack up when the true label is P but the model's predicted probability was Q.
WhyThis is the number a classifier's training loop actually computes and minimises, batch by batch.
Where in MLThe standard loss function for classifiers and next-token language models.
?From one surprise value to a training loss

13.2 computed the surprise of one outcome under the model's own probability for it: −log q, where q is the probability the model assigned to whatever the true label turned out to be. Do that for every example in a labelled batch and average the results — that average is cross-entropy, written H(P,Q), and it is exactly what a training loop calls "loss".

Training batch (true label from the ledger, model's predicted P(fraud) at training time):
T1: fraud, predicted 0.80 → q for the true class = 0.80 → −log₂(0.80) = 0.322
T2: not-fraud, predicted 0.05 → q for the true class = 0.95 → −log₂(0.95) = 0.074
T3: fraud, predicted 0.20 → q for the true class = 0.20 → −log₂(0.20) = 2.322
T4: not-fraud, predicted 0.03 → q for the true class = 0.97 → −log₂(0.97) = 0.044
sum = 0.322 + 0.074 + 2.322 + 0.044 = 2.762
H(P,Q) = 2.762 / 4 = 0.690 bits
T3 alone contributes more than the other three combined — the model gave the actual fraud case only a 20% chance, and that single bad call dominates the batch loss. That is exactly the behaviour you want from a loss: confident wrong answers hurt far more than uncertain ones.
what each symbol is q for the true classthe model's predicted probability of whichever label actually happened — 0.80 if it predicted fraud and fraud happened, 0.95 if it predicted 5% fraud and not-fraud happened H(P,Q)cross-entropy: the average of those four −log q values
Interview takeawayCross-entropy is the average −log(probability assigned to the true label) — a confident wrong answer costs far more than an uncertain one, which is exactly the incentive you want a loss function to create.

How much of that loss is the model's fault — KL divergence

entropy H(P) (13.4) + cross-entropy H(P,Q) (13.5) → their gap is the extra cost caused specifically by the model being wrong → KL divergence
WhatCross-entropy minus entropy — the excess surprise caused by the model's probabilities being off, on top of the surprise nobody could have avoided.
WhyIt isolates "how wrong is this model's distribution" from "how uncertain is this situation inherently."
Where in MLComparing two distributions you hold in hand — a production model against an audited truth, a teacher against a student, a policy before and after an update.
?Setting up the audited sample

Every transaction the model scored between 0.3 and 0.9 last week — the review band — got a manual audit. That is 100 transactions, and 5 of them really were fraud. The review band is a deliberately higher-risk slice of traffic, so 5% is not the same number as the population base rate of 0.5% quoted in module 12 — it is the rate within transactions the model was already unsure about.

The true distribution over that batch, from the audit, is P = [0.05, 0.95]. The model's own average predicted distribution over the same 100 transactions was Q = [0.03, 0.97] — the model was, on average, a little too optimistic about this batch.

P = 0.050.95  (audited truth)    Q = 0.030.97  (model's average prediction)
H(P) = −[0.05×log₂(0.05) + 0.95×log₂(0.95)] = −[−0.2161 − 0.0703] = 0.286 bits
H(P,Q) = −[0.05×log₂(0.03) + 0.95×log₂(0.97)] = −[−0.2529 − 0.0417] = 0.295 bits
DKL(P ‖ Q) = H(P,Q) − H(P) = 0.295 − 0.286 = 0.0083 bits
direct check: 0.05×log₂(0.05/0.03) + 0.95×log₂(0.95/0.97) = 0.0369 − 0.0285 = 0.0083 bits ✓
Both routes to DKL agree, because they are the same quantity: the 0.0083 bits is pure "model was a bit optimistic" cost, separate from the 0.286 bits of uncertainty that was there regardless of what the model believed. Gibbs' inequality guarantees DKL ≥ 0 always — you can decompose cross-entropy this way for any P and Q, and the excess term never goes negative; it hits exactly 0 only when Q matches P perfectly.
what each symbol is DKL(P ‖ Q)KL divergence from Q to P — read "the extra cost of using Q when P is the truth" H(P,Q) = H(P) + DKL(P ‖ Q)the identity just verified with real numbers: total cost = unavoidable cost + model's excess cost
?Why the direction is not symmetric

Swap which distribution plays "truth" and which plays "model", using the same two distributions:

DKL(Q ‖ P) = 0.03×log₂(0.03/0.05) + 0.97×log₂(0.97/0.95) = −0.0221 + 0.0291 = 0.0070 bits
DKL(P ‖ Q) = 0.0083 bits but DKL(Q ‖ P) = 0.0070 bits — different numbers from the same two distributions, just swapped. KL divergence is not symmetric, so it is not a distance in the mathematical sense. 13.12 works out why the direction changes what gets penalised.
Interview takeawayH(P,Q) = H(P) + DKL(P‖Q); since H(P) is fixed by the data, minimising cross-entropy during training and minimising KL divergence are the same optimisation.

Turning the loss into a count — perplexity

cross-entropy H(P,Q) (13.5) → exponentiate it back off the log scale → perplexity
WhatCross-entropy converted from a bit count back into an "effective number of equally likely options."
Why0.690 bits is hard to feel intuitively; perplexity restates the same number as a count you can compare to a coin flip.
Where in MLThe standard human-readable way to report language-model quality — same formula, applied to a much larger label space.
perplexity = 2^H(P,Q) = 2^0.690
= 1.61
For a two-outcome problem, perplexity ranges from 1 (perfect certainty) to 2 (a coin flip). 1.61 says the batch loss leaves the model about as confused as choosing between 1.6 equally likely options per transaction — clearly better than guessing, but T3's bad miss (13.5) keeps it well short of 1.
what each symbol is 2^H(P,Q)exponentiating with the same base used inside the log — base 2 here because the cross-entropy was computed in bits 1.61not a probability and not a bit count — an equivalent number of uniformly likely options
?Why perplexity for a language model looks so different

Same formula, bigger label space. A language model predicts over a vocabulary of tens of thousands of tokens instead of 2 outcomes, so its cross-entropy — and therefore its perplexity — sits on a completely different scale; a well-trained model might still show a perplexity in the tens. That is not a different quantity, just the same 2^H(P,Q) applied where the number of possible "next labels" is much larger than 2.

Interview takeawayPerplexity is exp(cross-entropy) — always derive it from a cross-entropy value you can defend, never quote it as a bare reference number.

Does the merchant category help — conditional entropy

WhatThe uncertainty left in the fraud outcome once you already know a feature's value, averaged over that feature's possible values.
WhyTests whether a candidate feature actually reduces uncertainty before you add it to the model.
Where in MLFeature evaluation, and — as "information gain" in 13.9 — the split criterion inside a decision tree.
?Splitting the audited sample by merchant category

Same 100 audited transactions from 13.6, now broken down by merchant category instead of collapsed into one number. 40 were electronics purchases, 4 of them fraud. 60 were groceries, 1 of them fraud. Check the totals: 4 + 1 = 5 fraud out of 100 — the same 5% from 13.6, just sliced a different way.

electronics: 4/40 fraud = 0.10    groceries: 1/60 fraud = 0.0167
H(Y|electronics) = −[0.10×log₂(0.10) + 0.90×log₂(0.90)] = −[−0.332 − 0.137] = 0.469 bits
H(Y|groceries) = −[0.0167×log₂(0.0167) + 0.9833×log₂(0.9833)] = −[−0.098 − 0.024] = 0.122 bits
H(Y|X) = 0.40×0.469 + 0.60×0.122 = 0.188 + 0.073 = 0.261 bits
H(Y|X) = 0.261 bits is below the unconditional H(Y) = 0.286 bits from 13.6 (same batch, not yet split by category). Knowing merchant category shrinks the average uncertainty about fraud — electronics is a genuinely riskier category (10% vs 1.67%), so learning it narrows things down.
what each symbol is Ythe fraud outcome — the thing we are uncertain about Xmerchant category — the feature we are testing H(Y|X)"entropy of Y given X" — H(Y|category), averaged over categories, weighted by how common each category is (0.40, 0.60)
Interview takeawayConditional entropy answers "how much uncertainty is left after this feature" — a feature is only useful if it makes this number smaller than the unconditional entropy.

How much did that feature actually help — mutual information

conditional entropy H(Y|X) (13.8) → subtract it from the unconditional H(Y) → mutual information
WhatThe drop in uncertainty about fraud once you know merchant category: H(Y) − H(Y|X).
WhyA single number for "how useful is this feature" — one that catches non-linear relationships correlation would miss entirely.
Where in MLFeature selection, and the decision-tree split criterion "information gain," which is this exact quantity computed per candidate split.
H(Y) = 0.286 bits  (13.6, unconditional)    H(Y|X) = 0.261 bits  (13.8, conditional on merchant category)
I(X;Y) = H(Y) − H(Y|X) = 0.286 − 0.261 = 0.025 bits
Merchant category buys you 0.025 bits of certainty about fraud, on average. Small in absolute terms because this batch was already narrowed to the review band, but the sign matters: it is positive, so the feature genuinely helps, and I(X;Y) can never be negative for any feature.
what each symbol is I(X;Y)mutual information — symmetric (I(X;Y) = I(Y;X)) and zero exactly when the two variables are independent
?Why mutual information catches what correlation misses

Suppose transaction amount and fraud have a U-shaped relationship: very small amounts (card testing) and very large amounts (cash-out) both carry elevated risk, while mid-sized amounts are comparatively safe. A linear correlation between amount and fraud would land close to zero — the relationship is not a straight line. But knowing the amount still clearly moves your fraud belief in either direction, so mutual information stays high. Correlation only sees straight-line relationships; mutual information sees any dependence.

Interview takeawayMutual information detects any dependence, not just linear ones — a feature can have zero correlation with the label and still be genuinely useful.

A symmetric alternative — Jensen–Shannon divergence

KL divergence (13.6) is directional and unbounded → average two KL terms against a shared midpoint → Jensen–Shannon divergence, symmetric and bounded
WhatBuild the midpoint M = (P+Q)/2, compute the KL from each of P and Q to M, and average the two.
WhyKL divergence is neither symmetric nor bounded; JS restores both properties while still measuring "how different are these two distributions."
Where in MLComparing two distributions when direction should not matter — it also underlies the original GAN training objective, where a generator's output distribution is compared against real data.
P = [0.05, 0.95]    Q = [0.03, 0.97]    M = (P+Q)/2 = [0.04, 0.96]
DKL(P ‖ M) = 0.05×log₂(0.05/0.04) + 0.95×log₂(0.95/0.96) = 0.0161 − 0.0144 = 0.0017 bits
DKL(Q ‖ M) = 0.03×log₂(0.03/0.04) + 0.97×log₂(0.97/0.96) = −0.0125 + 0.0145 = 0.0021 bits
JS(P,Q) = ½(0.0017 + 0.0021) = 0.0019 bits
JS = 0.0019 bits is smaller than either directional KL value (0.0083 and 0.0070 bits from 13.6) — both P and Q are close to their own midpoint. Swap P and Q in the formula and JS comes out identical, because the two KL terms just trade places inside a sum; that is what "symmetric" buys you over plain KL divergence. JS is also bounded: for two-outcome distributions it can never exceed 1 bit, however different P and Q are — a KL value has no such ceiling.
what each symbol is Mthe midpoint distribution — average P and Q entry by entry JS(P,Q)the average of the two KL-to-midpoint values
Interview takeawayJS divergence is symmetric and bounded where KL is neither — build it from two KL calculations you already know how to do, against a midpoint you construct yourself.

Why it has to be a logarithm

WhatThree requirements on a "how surprising" function — pin down the log as the only option.
Why"Because Shannon said so" is not an answer an interviewer will accept; the log is forced, not chosen.
Where in MLAlso explains why every framework computes losses in log-space, not just why entropy looks the way it does.
?The three requirements, checked against numbers already on this page
  1. Certainty carries no information. p = 1 must give 0, and log(1) = 0. ✓
  2. Rarer means more informative. −log₂(0.03) = 5.06 bits (13.2) is bigger than −log₂(0.97) = 0.04 bits — the function falls as p rises. ✓
  3. Independent information adds. If two facts are independent, learning both should give you the sum of their individual surprises. But independent probabilities multiply: P(both) = P(one)×P(other). You need a function that turns multiplication into addition — log(a×b) = log(a) + log(b) is the defining property of the logarithm, and no other function has it.

Requirement 3 is the whole answer: information is additive, probability is multiplicative, log is the bridge between them.

?The same fact, as a numerical-stability trick

Multiplying many probabilities together — say, the model's assigned probability for every transaction in a batch of ten thousand — underflows to exactly 0 in floating point, because each factor is below 1. Summing their logs instead never underflows that way, which is the real reason every framework computes cross-entropy as a sum of logs rather than a product of probabilities. This is the same log-turns-multiplication-into-addition fact from requirement 3, just used for arithmetic safety instead of for defining information.

Interview takeawayThe logarithm is not a stylistic choice — it is the unique function that makes independent surprise additive, and that same property is why computing in log-space avoids floating-point underflow.

KL is not a distance, and the direction is load-bearing

WhatDKL(P‖Q) ≠ DKL(Q‖P), and which distribution is weighted determines which kind of mistake gets punished.
WhyThe direction is a modelling decision with real behavioural consequences, not an arbitrary notational choice.
Where in MLForward KL: maximum-likelihood training, distillation. Reverse KL: variational inference, the RLHF/PPO penalty against a reference policy.

13.6 already showed the two directions give different numbers on the same pair of distributions — 0.0083 bits forward, 0.0070 bits reverse. The general pattern behind that gap:

Forward — DKL(P‖Q)Reverse — DKL(Q‖P)
Weighted bythe truth Pthe model Q
PunishesQ too small where P is large — the model calling something rare that really isn'tQ too large where P is small — the model calling something likely that really isn't
You meet it inordinary supervised training, MLE, distillation on the full distributionvariational inference, the KL penalty that keeps an RLHF-tuned policy close to its reference policy
Interview takeawayDKL(P‖Q) fails symmetry and the triangle inequality, so it is not a distance — say which direction you mean, because forward and reverse KL penalise different kinds of mistake.

Has the world changed — the Population Stability Index

KL divergence compares two distributions you hold at one moment → symmetrise it and bin it over time → PSI, the standard production drift alarm (module 54)
WhatBin a score into buckets, compare the proportion of transactions in each bucket now against a reference period, and sum a symmetrised, KL-flavoured penalty over the buckets.
WhyA single number that flags "the model's output distribution has shifted" before accuracy visibly drops, using only score data — no fresh labels required.
Where in MLContinuous production monitoring; module 54 covers the monitoring pipeline this feeds.
Bin the fraud score using the thresholds from 13.1: allow (<0.3), review (0.3–0.9), block (>0.9). Proportion of all transactions in each bin:
reference month: allow 0.850, review 0.120, block 0.030
current month: allow 0.780, review 0.150, block 0.070
PSI = Σ (current − reference) × ln(current / reference)
allow: (0.780−0.850)×ln(0.780/0.850) = (−0.070)×(−0.0860) = 0.0060
review: (0.150−0.120)×ln(0.150/0.120) = (0.030)×(0.2231) = 0.0067
block: (0.070−0.030)×ln(0.070/0.030) = (0.040)×(0.8473) = 0.0339
PSI = 0.0060 + 0.0067 + 0.0339 = 0.0466
More transactions are landing in review and block than at reference time — the score distribution has drifted upward. By the common credit-scoring convention, PSI below 0.1 is "no meaningful shift," 0.1–0.25 is "moderate," above 0.25 is "investigate now." 0.0466 sits under the first threshold: a real but mild shift, worth a note rather than an alarm. Those threshold numbers are convention, not theory — calibrate them against your own historical drift rather than citing them as law.
what each symbol is ln(·)natural log, used here by PSI convention rather than log₂ — the choice of base still only rescales the result, per 13.3 (current − reference) × ln(current/reference)PSI's per-bin term — symmetric in current and reference by construction, so swapping the two periods gives the same total
Interview takeawayPSI is a symmetrised, binned KL-style comparison between two time periods of the same score — cheap to compute, needs no fresh labels, and its thresholds are calibration conventions rather than statistical laws.

Questions

BASICWhat is entropy, in plain language?
The average surprise baked into a distribution — how uncertain the model's own belief already is, before you check whether it was right.

For the transaction the model scored 97% not-fraud, entropy is 0.194 bits — the model is fairly confident, so there isn't much uncertainty left to average over. A genuine coin flip (50/50) gives the maximum possible entropy for two outcomes, exactly 1 bit.

Where it earns its keep: entropy is the floor on average achievable loss for that distribution. If the true label distribution for a batch has entropy 0.286 bits (13.6), no model gets its cross-entropy below that in expectation — a training loss approaching zero on genuinely ambiguous data is a sign of memorisation, not a great model.

Trap

Entropy is a property of a distribution, not of one sample. "This batch has high entropy" is loose talk unless you say which distribution over what — the model's predictions, or the true labels.

BASICWhat is the difference between cross-entropy and KL divergence?
Cross-entropy is the total cost of using the model's probabilities instead of the truth; KL divergence is just the excess part — cross-entropy minus the entropy that was unavoidable anyway.

On the audited batch: H(P) = 0.286 bits, H(P,Q) = 0.295 bits, so DKL(P‖Q) = 0.009 bits is the model's fault specifically. Since H(P) belongs to the data and not to the model's parameters, it stays constant during training — minimising cross-entropy and minimising KL divergence are the same optimisation, differing only by a constant no optimiser can touch.

Why bother with both: cross-entropy is the practical loss, because you never actually know H(P) for the true data-generating process. KL divergence is the right quantity once you hold two distributions you both know explicitly — a production model against an audited sample, or a reference policy against a fine-tuned one.

Trap

"So loss should go to zero?" Only if the labels are deterministic given the inputs. On real fraud data H(P) is well above zero — two identical-looking transactions can have different outcomes — so a near-zero training loss is a symptom of leakage or memorisation, not success.

MIDWhy a logarithm? Why not just use 1/p or (1−p)?
Because information from independent events must add, while their probabilities multiply — and the logarithm is the unique function that converts one into the other.

Write down the three properties from 13.11: zero surprise at p=1; more surprise for rarer events; and additivity for independent events. That functional equation forces a logarithm up to a choice of base — base 2 gives bits, base e gives nats.

1/p fails additivity: 1/(a×b) does not equal 1/a + 1/b. (1−p) fails it too, and also gives a finite surprise value to an impossible event (p→0 gives 1−p→1, not infinity), which is the wrong behaviour.

The practical bonus: the likelihood of a batch is a product of many probabilities below 1, which underflows to exactly 0 in float32. Logs turn that product into a sum that stays numerically fine — the same additivity property, used for arithmetic safety instead of for defining information.

Trap

Never compute log(softmax(x)) yourself in code: softmax can underflow to exactly 0, and the log of 0 is −infinity. The fix is the log-sum-exp trick: subtract the largest input value from every entry before exponentiating, which keeps every intermediate exponential in a safe numeric range without changing the final answer (a fixed shift cancels out of the normalisation). log_softmax is a fused operation that does exactly this, which is why it exists as its own function rather than a log applied after a separate softmax.

MIDWhat does perplexity mean, and how do you read a value like 1.61?
Perplexity is the exponential of cross-entropy — the effective number of equally likely options the model is choosing between, on average, per prediction.

Our training batch had cross-entropy 0.690 bits, so perplexity is 2^0.690 = 1.61 (13.7). For a two-outcome problem, perplexity ranges from 1 (perfect certainty every time) to 2 (indistinguishable from a coin flip). 1.61 says the model is doing meaningfully better than guessing but is still dragged down by the one confident wrong call in the batch (T3, 13.5).

The same formula applied to a language model, where the label space is tens of thousands of tokens instead of 2, produces perplexity values on a much larger scale — but it is always the same computation: exponentiate whatever cross-entropy you can defend.

Trap

Perplexity is only comparable between models scored on the same label space with the same granularity. A binary classifier's perplexity and a language model's perplexity are not on a comparable scale, and neither are two language models with different tokenizers — a model with a larger vocabulary packs more text per prediction and gets a lower perplexity for free.

MIDWhat is mutual information, and how does it differ from correlation?
Mutual information is how much knowing one variable reduces uncertainty about another — and unlike correlation, it detects any dependence, not just linear ones.

I(X;Y) = H(Y) − H(Y|X). On the audited batch, merchant category gave I(X;Y) = 0.025 bits (13.9) — small but strictly positive, because electronics (10% fraud) and groceries (1.67% fraud) genuinely differ.

The canonical case where correlation fails and mutual information does not: transaction amount could have a U-shaped relationship with fraud, elevated at both very small and very large amounts and low in between. A linear correlation would land near zero, because there is no straight-line relationship — but knowing the amount still clearly moves your fraud belief, so mutual information stays meaningfully above zero.

Under the name information gain, this exact quantity is the split criterion in a decision tree: the reduction in label entropy achieved by splitting on a candidate feature.

Trap

Mutual information has no fixed upper bound and no natural scale the way correlation's [−1, 1] does, so "I(X;Y) = 0.4" is not interpretable on its own — you need to compare it against the unconditional entropy H(Y) it was computed from, the way 0.025 only means something next to the 0.286 it was subtracted from.

SENIORExplain forward versus reverse KL, and why the direction changes what you get.
Forward KL is mode-covering and reverse KL is mode-seeking, because whichever distribution sits in front of the log is the one whose regions get penalised most heavily.

On the audited batch, DKL(P‖Q) = 0.0083 bits and DKL(Q‖P) = 0.0070 bits (13.6) — different numbers from the same two distributions. Forward, DKL(P‖Q): the expectation is taken under the true P, so wherever P has mass and Q assigns it little, the log ratio grows large and gets a big weight from P. Q is pushed to put probability everywhere P does. This is what maximum-likelihood training does — it is why a model fit this way tends to spread out and cover every mode of the true distribution, including low-density regions between them.

Reverse, DKL(Q‖P): the expectation is taken under Q, so a region where Q assigns near-zero probability costs almost nothing, whatever P does there. Q can safely ignore entire regions of P; what it cannot do is put mass where P has none. This collapses onto one region and represents it precisely.

Where it shows up concretely: supervised training and distillation on a full soft-label distribution use forward KL, because the goal is to reproduce the whole distribution. The RLHF/PPO penalty that keeps a fine-tuned policy close to its frozen reference policy typically uses the reverse direction — the tuned model is discouraged from drifting into gibberish, while being allowed to ignore output regions the reference itself puts little weight on.

Trap

If asked which direction is "correct," neither is — it is a modelling choice about which failure mode you can live with: spreading probability everywhere versus collapsing onto part of the distribution.

SENIORWhere does KL divergence show up in a production ML system?
In several places that look unrelated until you notice they are the same quantity: the training loss, the RLHF penalty, knowledge distillation, and drift detection.
  • Training. H(P,Q) = H(P) + DKL(P‖Q) (13.6), so every classifier you have ever trained with cross-entropy was minimising a KL divergence it never named.
  • RLHF / PPO. A KL penalty against a frozen reference policy keeps a fine-tuned model from drifting into reward-hacked nonsense. Its coefficient is one of the few genuinely important knobs in the pipeline: too small and the model degenerates, too large and it barely moves from the reference.
  • Distillation. A student model matches a teacher's full soft output distribution, which is a forward KL. The relative probabilities the teacher assigns to wrong classes — sometimes called "dark knowledge," because it is information hidden inside the non-top predictions rather than in the hard label — carry signal that a single correct-answer label does not, and KL is what transfers it.
  • Drift detection. PSI (13.13) bins a score's distribution and compares reference against current, using a symmetrised KL-style penalty per bin — symmetrised specifically so the number does not blow up when a bin has very few observations in one period.

The warning that ties all four together: KL diverges to infinity when the comparison distribution assigns exactly zero probability to something the reference distribution does not. In practice, every implementation smooths, clips, or drops empty bins before computing it, and how you handle that choice materially changes your alert rate or your training signal.

Trap

PSI's textbook thresholds — 0.1 "moderate," 0.25 "significant" — are credit-scoring convention, not derived from theory, and they depend on how you chose your bins. State them as starting points you would recalibrate against your own historical drift, not as fixed laws.
